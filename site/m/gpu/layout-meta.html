A boundary with no type checker

Between a GPU buffer write and a GLSL block there is no type. The driver copies bytes; the shader casts them to whatever its own declaration says they are. Nothing in the Vulkan API, the SPIR-V validator or the C++ compiler compares the two, and a mismatch yields neither a validation error nor a crash — it yields a plausible wrong image. `layout_meta.hpp` converts the one part of that risk that is mechanically checkable, the byte size of the C++ side, into a compile error. Five canonical constants live there. Four are bare literals — `kGPULightBytes` is `80` with `// 5 * vec4` beside it, `kPTPushConstantsBytes` a bare `256` — so the number and its justification can drift apart unwatched. The fifth is the arithmetic the material pack implies:

inline constexpr std::size_t kMaterialBytes = kMaterialVec4s * sizeof(glm::vec4);ohao/gpu/layout_meta.hpp:26

Nor is the header purely declarative: `MaterialGpuPack` adds two constexpr accessors for the three-`vec4` material stride and pins them with static asserts against hand-computed answers, so an edit to `kMaterialVec4s` fails here rather than in a shader.

What the two assertions actually prove

`OHAO_ASSERT_GPU_LAYOUT(Type, Bytes)` expands to a pair of static asserts. The second is the obvious one:

static_assert(sizeof(Type) == (Bytes), \ohao/core/concepts.hpp:81

The first requires `GpuPod`, which is `is_trivially_copyable_v` **and** `is_standard_layout_v`. Trivial copyability makes the `memcpy` into mapped device memory defined behaviour instead of a habit. Standard layout is the half people skip, and the one doing structural work: it forbids reordering members declared across different access-control sections, guarantees the first member sits at offset 0, and is the precondition for `offsetof` being defined at all. Without it a struct could satisfy the size check while the field order the shader assumes does not formally exist.

Neither assertion says anything about the other side of the boundary — both are statements about C++ types, evaluated by the C++ compiler, and no build step reflects the SPIR-V. The macro catches *someone added a float to the struct* and is blind to *someone reordered the GLSL block*. Three structs carry it: `LightData` at 128 bytes, `GPULight` at 80 and `PTPushConstants` at 256. The first rides in the deferred light UBO, the second in the path tracer's light SSBO; only the third crosses a push-constant boundary.

The structs that make up the render world's tables are guarded by plain `static_assert(sizeof(...) == N)` instead, which proves the size and nothing about `GpuPod`:

static_assert(sizeof(InstanceGpu) == 160);ohao/render/scene/render_scene_types.hpp:124

`InstanceGpu` (160), `MeshGpu` (16), `Vertex` (100, which the RT shaders read as 25 floats) and the G-buffer's `CameraUBO` (128) are pinned this way. The practical difference is small — each is a plain aggregate — but it means the macro's trivially-copyable half is applied to three of the structs the GPU reads and not to the rest.

The one block above the guaranteed floor

Vulkan guarantees only 128 bytes of push-constant space; anything above that is a device capability, not a promise. Exactly one contract sits above the floor — the path tracer's 256 — and no code queries `maxPushConstantsSize`; across `ohao/`, `shaders/` and `examples/` the identifier occurs once, inside a comment. On a minimum-spec device the failure surfaces at pipeline-layout creation, not at compile time. The raster blocks are far below the line: the G-buffer pushes 16 bytes and the shadow pass 64.

The path-tracer block is also the one with no headroom. When a per-frame sample count had to reach the raygen shaders there was no room for another field:

// 256-byte device maxPushConstantsSize, so we cannot append a field — theohao/render/rt/path_tracer_render.cpp:676

so it was folded into the top half of a lane that already held the bounce limit:

const uint32_t packedBouncesAndSpf = (spf << 16) | (m_maxBounces & 0xFFFFu);ohao/render/rt/path_tracer_render.cpp:680

The base and offline raygens mask the high bits off; the realtime raygen loops on them. A size contract that is exactly satisfied has stopped being a check and become a design constraint.

The per-draw block that shrank to a slot

The raster per-draw contract is a single `uint`, padded to a 16-byte multiple. Per-object state lives in tables the shaders index, and the push constant only names which submesh material slot the draw uses:

static_assert(sizeof(DrawPushConstant) == 16);ohao/render/deferred/gbuffer_pass.hpp:131

`gbuffer.frag` declares only the four bytes it reads, so the block it declares is shorter than the range the pass pushes:

layout(push_constant) uniform PushConstants { uint materialSlot; } pc;shaders/core/gbuffer.frag:42

That is legal — a shader may declare a prefix of the pushed range — but it means the size assertion pins the C++ struct, not the GLSL block, and the three padding words exist only to keep the range at a 16-byte multiple. The material slot is not a material: the shader resolves it through the instance's reference list, so the contract that matters is the table layout below, not the push block.

The instance table is the boundary that carries the weight. `InstanceGpu` is declared once in C++ and once in `scene_data.glsl`, whose header names its twin:

// Matches ohao/render/scene/render_scene_types.hpp (std430).shaders/includes/scene/scene_data.glsl:3

Six shaders include that file — both G-buffer stages, the shadow vertex shader, and the path tracer's closest-hit, any-hit and GI closest-hit — so a layout edit has to be made in exactly two places, and only the C++ half is size-checked. The declaration is shared across shaders but not across the language boundary.

One packer, two readers

The material rows are where the deferred and path-traced pipelines meet. The G-buffer pass and the path tracer read the same 48-byte rows out of one storage buffer, and one function writes them:

d.roughness, d.metallic, bits(d.normalTex), bits(d.emissiveTex),ohao/render/scene/material_table.cpp:36

The size of a row is asserted against `MaterialGpuPack::kBytes`:

static_assert(sizeof(Pack) == layout::MaterialGpuPack::kBytes);ohao/render/scene/material_table.hpp:19

but which float is which lane is not, and each reader restates it in a comment beside its own decode — in `gbuffer.frag`:

vec4 row1 = matRows[m * 3u + 1u]; // roughness, metallic, normalTex, emissiveTexshaders/core/gbuffer.frag:60

and in the closest-hit shader:

vec4 matParams = matColorBuf.matColors[matID * 3u + 1u]; // (roughness, metallic, normalTexIdx, emissiveTexIdx)shaders/rt/pt_closesthit.rchit:109

All three agree today. Because there is a single packer the two pipelines cannot disagree about lane order, but the agreement is three hand-written copies of one diagram, with the size assert as the only mechanical witness. A reordered row needs three coordinated edits and fails only as wrong pixels.

Two sentinel decoders in one shader

Inside `gbuffer.frag` the "no texture" value is decoded two different ways. Albedo and normal compare against the sentinel; roughness-metallic and emissive compare against a magnitude instead:

if (roughMetalTexIdx < 4096u) {shaders/core/gbuffer.frag:108

4096 is not arbitrary — it is the bindless array's capacity as the renderer constructs the manager:

if (!m_textureManager->initialize(m_device, m_physicalDevice, nullptr, 4096,ohao/gpu/vulkan/renderer.cpp:126

The two tests agree on every value the packer produces, so this is not a live bug; it is a hazard in two directions. `< 4096u` rejects a garbage lane and `!= 0xFFFFFFFFu` does not — so if a lane ever carries an arbitrary bit pattern, the albedo and normal lookups pass the sentinel test and index `textures[]` with it, while the other two reject it. And the bound is a literal, so raising `maxTextures` past 4096 hides the high descriptors from two of the four lookups and leaves them visible to the other two. The path tracer's closest-hit does not share the hazard: it clamps every index against a specialisation constant that tracks the capacity actually bound.

uint boundTexture(uint idx) { return idx < OHAO_BINDLESS_COUNT ? idx : 0xFFFFFFFFu; }shaders/rt/pt_closesthit.rchit:47

What reaches the GPU from a material

The GPU-facing description of a material is `render::MaterialDesc`: a base colour, roughness, metallic, four bindless texture indices (albedo, normal, roughness-metallic, emissive) and an emissive strength — eight members packed into twelve floats, the last two of them unused.

bits(d.roughMetalTex), d.emissiveStrength, 0.0f, 0.0f,ohao/render/scene/material_table.cpp:37

The authoring struct in `material.hpp` is a different thing. `Material` carries thirty-one members — index of refraction, transmission, clear coat, subsurface colour and radius, normal intensity, height scale, nine texture paths and the seven `use*` flags gating them, and a thirteen-value preset enum whose `Custom` case is an explicit no-op, leaving twelve presets. None of them reach a GPU buffer: nothing outside `material.cpp` constructs a `Material`, and the render world takes a `MaterialDesc` instead. The preset constructors still run if called — `Type::Glass` sets a transmission of 0.9 — but no pipeline has a field to receive it. Nothing checks that gap, because there is nothing to check against: `Material` is not a GPU struct and carries no layout assertion.

A material system that was finished and never connected

`material_instance.hpp` holds a second, complete material stack: a 176-byte `PBRMaterialParams` with eight bindless texture indices and a thirteen-flag feature mask, a `MaterialInstance` with clamped setters and dirty tracking, and a `MaterialManager` that allocates a persistently mapped storage buffer for 1024 materials, builds its own descriptor set layout and flushes only the dirty rows. Outside `tests/renderer/renderer_pipeline_tests.cpp` nothing in `ohao/` or `examples/` constructs a `MaterialManager`, and no block in `shaders/` declares a matching layout. The render world's `MaterialTable` is a separate, smaller design that is wired in. Its guard reflects that — not the engine macro but a weaker pair, `GpuPod` plus a modulo:

static_assert(sizeof(PBRMaterialParams) % 16 == 0, "PBRMaterialParams must be 16-byte aligned");ohao/gpu/vulkan/material_instance.hpp:129

An alignment check pins the struct to no particular size: any edit adding or removing a multiple of 16 bytes passes. Right strength with no shader on the other end, wrong strength the day one appears.

Why

Sizes are pinned from a constants header rather than derived from the shaders. The alternative — one declaration shared by both sides, either a header the GLSL `#include`s or SPIR-V reflection at pipeline creation — makes *offsets* checkable, not just totals. The toolchain already supports the include half, and the render world uses it: `scene_data.glsl` is included by six shaders. But `shaders/includes/common/types.glsl` declares the 128-byte `Light` struct once, and no shader includes it — `deferred_lighting.frag`, the one shader that reads `LightData`, includes only `encoding.glsl` and `brdf_ggx.glsl` and re-declares the same struct by hand. Shared declaration is therefore in use where the scene tables are new and routed around where the light block is old. Its cost is that every C++ struct becomes downstream of shader preprocessing and layout questions become runtime failures. OHAO took the cheap half — one place to edit a size, review for everything else.

Key idea

`OHAO_ASSERT_GPU_LAYOUT` proves two things about a C++ type: that it can be memcpy'd, and that it is N bytes. It cannot see the GLSL that reads those bytes, so every defect that leaves the total unchanged — a reordered field, a lane that changed meaning, a shader block written against an older struct — passes it.

Contracts

  • `PTPushConstants` sits exactly at the 256-byte limit the code assumes, so no field can be appended. `params.w` carries `samplesPerFrame` in its high 16 bits and `maxBounces` in its low 16; the realtime raygen unpacks the high half, base and offline mask it off.
  • Nothing queries `maxPushConstantsSize`, and the path tracer's block exceeds Vulkan's guaranteed 128 bytes. On a minimum-spec device the failure is a rejected pipeline layout, not a failed build.
  • Three structs carry `OHAO_ASSERT_GPU_LAYOUT` (`LightData`, `GPULight`, `PTPushConstants`); `InstanceGpu`, `MeshGpu`, `Vertex`, `CameraUBO` and `DrawPushConstant` are size-checked with a bare `static_assert`. A layout edit must update the C++ struct, its GLSL twin and the assert together.
  • `InstanceGpu` exists once in C++ and once in `scene_data.glsl`; six shaders read the GLSL copy. Only the C++ side is size-checked.
  • `MaterialTable::pack` is the only writer of the three-`vec4` material row; `gbuffer.frag` and `pt_closesthit.rchit` each decode it by hand. The row size is asserted, the lane order is not.
  • `gbuffer.frag` decodes one sentinel two ways — `!= 0xFFFFFFFFu` for albedo and normal, `< 4096u` for roughness-metallic and emissive. That literal must track the texture manager's `maxTextures` by hand; the path tracer's equivalent is a specialisation constant.
  • `Material` in `material.hpp` has no GPU consumer; add a field to `MaterialDesc`, not to `Material`, to reach a shader.
  • `PBRMaterialParams` is guarded only by `sizeof % 16 == 0`. If a shader ever binds it, replace that with an exact-byte `OHAO_ASSERT_GPU_LAYOUT` first.
