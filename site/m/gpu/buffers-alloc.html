The allocator that serves one subsystem

OHAO compiles the whole Vulkan Memory Allocator into the engine. `gpu_allocator.cpp` is the translation unit that defines `VMA_IMPLEMENTATION`, so every OHAO binary carries VMA's suballocator and memory-type heuristics.

#define VMA_IMPLEMENTATIONohao/gpu/vulkan/gpu_allocator.cpp:12

Exactly one subsystem allocates through it: the render world. `RenderScene` owns a `GpuAllocator` as a member, and every buffer its tables hold — the mesh arenas, the material, instance and light tables, the TLAS instance buffer, and the per-frame staging buffers — comes from it.

GpuAllocator allocator;ohao/render/scene/render_scene.cpp:26
a.buf = m_ctx.allocator->createBuffer(elemSize * capacity, usage, AllocationUsage::GpuOnly);ohao/render/scene/mesh_registry.cpp:60

The other `GpuAllocator` in the tree is a smoke test:

GpuAllocator allocator;tests/renderer/renderer_pipeline_tests.cpp:632

The two other subsystems that hold a `GpuAllocator*` — `RenderGraph` and `BindlessTextureManager` — are handed a null pointer by the code that builds them (the render graph through a defaulted argument in `deferred_renderer.cpp`), and neither ever dereferences it:

if (!m_textureManager->initialize(m_device, m_physicalDevice, nullptr, 4096,ohao/gpu/vulkan/renderer.cpp:126

Counting call sites settles the shape: 73 raw `vkAllocateMemory` calls across 27 `.cpp` files under `ohao/`, against exactly two `vmaCreateBuffer`/`vmaCreateImage` calls, both inside `gpu_allocator.cpp` itself. Render targets, bindless texture images, shader binding tables, acceleration-structure storage and every readback buffer still own a private `VkDeviceMemory`; the scene's geometry and tables do not.

Why

Routing the engine through `GpuAllocator` depended on one flag. VMA must be told at creation time that it may return memory usable with `vkGetBufferDeviceAddress`, and the render world's arenas and TLAS instance buffer are created with `VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT`. The allocator now sets it, with a comment explaining what goes wrong without it — VMA silently skips the allocate flag in release builds, and the later address query is invalid: {{cite ohao/gpu/vulkan/gpu_allocator.cpp "allocatorInfo.flags |= VMA_ALLOCATOR_CREATE_BUFFER_DEVICE_ADDRESS_BIT;"}} The flag tags every block, so the device must have been created with `bufferDeviceAddress`, which the logical-device setup guarantees. The remaining raw allocations are the ones that chain `VK_MEMORY_ALLOCATE_DEVICE_ADDRESS_BIT` into their own allocate info — acceleration-structure scratch and storage in `rt_acceleration_structure.cpp`, and every shader binding table, with one each in `path_tracer_pipeline.cpp`, `rt_shadow_technique.cpp` and `rt_gi_technique.cpp`. {{cite ohao/render/rt/path_tracer_pipeline.cpp "VK_BUFFER_USAGE_SHADER_BINDING_TABLE_BIT_KHR |"}} Those would need their own review before moving over; the flag does not block it.

The class forces a dedicated `VkDeviceMemory` block for anything over 256 KB, and unconditionally for images.

if (size > 256 * 1024) { // 256KB thresholdohao/gpu/vulkan/gpu_allocator.cpp:143

Suballocating large resources out of shared blocks is most of what an allocator is for, and the render world's biggest buffers all cross that line — the vertex arena starts at a million vertices of 100 bytes — so for them `GpuAllocator` returns one allocation per buffer. The saving is in the small tables and the staging buffers, and in the accounting.

The leak counter both sides must agree on

`AllocationStats` is maintained by hand, and its two sides must use the same number. `destroyBuffer` debits `VmaAllocationInfo::size`, what VMA actually reserved:

VkDeviceSize size = buffer.allocation.getSize();ohao/gpu/vulkan/gpu_allocator.cpp:210

VMA documents that field as possibly *greater* than the requested size — the allocation absorbs alignment padding. `currentUsage` is an unsigned `std::size_t`, so a credit of the caller's requested size would let each padded buffer drift the running total downward, and the first debit that exceeded what was left — destroying the last live buffer would do it — would wrap the subtraction to a value near $2^{64}$. So the buffer path credits the VMA allocation size, the same quantity the debit uses and the same one `createImage` credits:

const VkDeviceSize accountedSize = result.allocation.getSize();ohao/gpu/vulkan/gpu_allocator.cpp:175

Nothing polls the counter mid-run: `hasLeaks()` and `liveBytes()` are defined on `AllocationStats` and called from nowhere in `ohao/`, `tests/` or `examples/`. The only reader is teardown, where `shutdown()` reads `currentUsage` directly and prints a leak warning when it is nonzero. `RenderScene::shutdown` destroys its tables first and the allocator last, so a buffer it forgot to release is exactly what that warning reports.

if (m_stats.currentUsage > 0) {ohao/gpu/vulkan/gpu_allocator.cpp:104

Device-local for the scene, host-visible for the leftovers

The scene's geometry and tables are `GpuOnly`: nothing maps them, and every write is a copy. The host-visible allocations that remain are the ones the CPU rewrites often or reads back. Each frame slot owns one persistently mapped staging buffer in the render world, grown when a frame's dirty bytes exceed it:

AllocationUsage::CpuToGpu, true);ohao/render/scene/render_scene.cpp:181

and the light uniform buffers the deferred lighting pass binds, one per frame slot, are raw `vkAllocateMemory` memory, host-visible and coherent, mapped once at init and never unmapped. The host writes a slot's buffer only after that slot's fence wait:

vkMapMemory(m_device, m_lightBufferMemory[slot], 0, bufferSize, 0, &m_lightBufferMapped[slot]);ohao/gpu/vulkan/buffer_setup.cpp:38

A mesh is therefore resident once, in device memory, whether it is drawn, traced or used as a BLAS input; there is no host-visible twin. In exchange every change to the scene costs a staged copy recorded into a frame's command buffer instead of a `memcpy` through a mapping, which is why edits are batched into contiguous runs.

The far plane the cascades are told

`renderDeferred` hands `DeferredRenderer` the camera's own view and projection, which it uses for the GBuffer, the lighting pass and SSR. The camera is default-constructed and nothing in the tree calls `setPerspectiveProjection`, so its clip planes stay at the constructor's 0.1 and 100.

float farPlane{100.0f};ohao/render/camera/camera.hpp:81

The `0.1f, 1000.0f` passed alongside the matrix are not clip planes and never reach a projection. They land in `m_nearPlane`/`m_farPlane`, whose only consumer is the cascaded shadow map:

m_deferredRenderer->setCameraData(view, proj, camPos, 0.1f, 1000.0f);ohao/gpu/vulkan/render_dispatch.cpp:93
m_csmPass->setCameraData(m_view, m_proj, m_nearPlane, m_farPlane);ohao/render/deferred/deferred_renderer.cpp:227

The real defect is there. `calculateCascadeSplits` blends a logarithmic and a linear split across $[n, f]$, and `calculateLightViewProj` then walks the camera's own frustum corners by the fraction $(d - n)/(f - n)$. Both halves must use the same $f$ or they describe different volumes — and they do not: the splits run out to 1000, the corners come from a projection that clips at 100.

float d = m_splitLambda * log + (1.0f - m_splitLambda) * linear;ohao/render/deferred/csm_pass.cpp:498

With the shipped `m_splitLambda` of 0.95 and four cascades the splits land near 13.5, 34.5, 132.5 and 1000. `selectCascade` in `deferred_lighting.frag` compares view depth against those, so a fragment 30 units out picks cascade 1 — whose matrix, rescaled over the 100-unit frustum, actually covers depth 1.4 to 3.5. The three near cascades are compressed into the first ~13 world units of a 100-unit view, and most of what is routed to them falls outside their shadow maps.

Eight slots, two type encodings

Lights are a fixed array, not a growable list. `LightData` is four `vec4`s plus a `mat4` light-space matrix — 128 bytes — and the uniform block holds eight:

constexpr uint32_t MAX_LIGHTS = 8;ohao/render/scene/render_scene_types.hpp:32

`LightTable::set` builds the array once per light-list change: regular lights in creation order first, then the emissive-mesh proxies appended, both capped at eight, so a scene with eight explicit lights drops every emissive light without a warning. Exactly one light in the buffer may cast a shadow — a latch takes the first qualifying one and every later light gets a shadow index of −1 and an identity light-space matrix:

int shadowCasterIndex = -1; // Index of first shadow-casting lightohao/render/scene/light_table.cpp:120

Which light qualifies is where two enumerations collide. `LightData.position.w` carries the *shader* type (0 = directional, 1 = point, 2 = spot), and a two-way ternary remaps the source `LightKind` into it — `Point` to 1, `Directional` to 0, anything else to 2:

const int deferredType = (d.kind == LightKind::Point) ? 1 : (d.kind == LightKind::Directional) ? 0 : 2;ohao/render/scene/light_table.cpp:127

Further down the same iteration the shadow test re-reads the source kind and accepts only point and spot:

if (d.kind == LightKind::Point || d.kind == LightKind::Spot) {ohao/render/scene/light_table.cpp:135

An authored directional light therefore never claims the shadow slot, while a point light does — and `lightSpaceMatrix`, dispatching on the already-remapped `position.w = 1`, matches neither its directional nor its spot branch and returns identity. The synthesized fallback sun is unaffected: it is written directly as shader type 0 and takes the orthographic branch. That is why the defect hides — shadows look right until someone adds a light to the scene.

The ternary's "anything else" arm hides a second collision. `LightType` has a fourth enumerator, `AreaRect`, with no branch of its own, so the raster light buffer emits it as a spot light carrying the component's default 30°/45° cone along the entity's -Z axis. It is not a hypothetical enumerator — `turntable.cpp` authors a ceiling area panel for its Cornell mode, and the RT path reads the same light correctly, packing both edge vectors and the derived area into `GPULight`:

enum class LightType : uint8_t { Point, Directional, Spot, AreaRect };ohao/ecs/components.hpp:58
area.type = ecs::LightType::AreaRect;examples/turntable.cpp:193
if (d.kind == LightKind::AreaRect) {ohao/render/scene/light_table.cpp:183

The two pipelines therefore disagree about what that entity is: a rectangle to the path tracer, a cone to the rasteriser.

The default light and its $\pi$

If the scene contributed nothing, a default directional light is synthesized with intensity $\pi$ and a warm tint:

defaultLight.color = glm::vec4(1.0f, 0.98f, 0.95f, glm::pi<float>());ohao/gpu/vulkan/buffer_setup.cpp:84

The $\pi$ is not decoration; it calibrates against the $1/\pi$ in an energy-conserving diffuse lobe. Take the Lambertian idealisation first: a BRDF of $\rho/\pi$ gives, for a light of intensity $I$,

$$ L_o = I \cdot \frac{\rho}{\pi} \cos\theta $$

with $\rho$ the base colour and $\theta$ the angle between surface normal and light direction. Setting $I = \pi$ makes a white albedo return $L_o = 1$ head-on — a clean reference white — instead of $1/\pi \approx 0.318$, which is $\log_2 \pi \approx 1.65$ stops underexposed.

The shipping lobe is not Lambert. The deferred lighting pass, the one consumer of this buffer, calls `evaluateBRDF`, whose diffuse term is Burley/Disney scaled by $k_D = (1 - F)(1 - m)$ for Fresnel $F$ and metalness $m$:

return diffuseColor * INV_PI * lightScatter * viewScatter;shaders/includes/brdf/brdf_common.glsl:92
vec3 kD = (vec3(1.0) - F) * (1.0 - surface.metallic);shaders/includes/brdf/brdf_ggx.glsl:146

Burley's two scatter factors both go to 1 at normal incidence, so it does collapse to $\rho/\pi$ exactly where the calibration is aimed — but $k_D$ trims 4% off a dielectric at $F_0 = 0.04$, and the Kulla-Conty multi-scatter term adds a little back. $I = \pi$ lands near reference white, not on it.

Emissive meshes flattened into point lights

`emissiveProxy` runs once per model upload and converts an emissive material into a point-light proxy — the cheap stand-in for real mesh-light sampling. For the first emissive-textured material it walks the texels, keeps those above a Rec. 709 luminance of 0.05, and averages the survivors into a colour:

const float lum = pr * 0.2126f + pg * 0.7152f + pb * 0.0722f;ohao/render/scene/model_upload.cpp:139

The 8-bit texels are divided by 255 with no transfer-function decode, so threshold and average are computed in whatever encoding the loader stored, not in linear radiance. Intensity is the summed luminance scaled by 0.1 and clamped:

light.intensity = std::min(totalPower * 0.1f, 20.0f);ohao/render/scene/model_upload.cpp:156

Because `totalPower` accumulates per texel, the same lamp authored at 4K and at 256² yields very different intensities — brightness scales with texture resolution, not emitting area. The light is also placed at the centre of the *whole model's* bounding box rather than the emissive material's triangles, and the scan stops after one material:

return std::nullopt; // one light per model: only the first emissive material countsohao/render/scene/model_upload.cpp:159

A character with an emissive visor and emissive boot strips gets one light, floating at the character's centroid. In the raster array it sits after the regular lights, so it is the first thing a full light list drops.

vk_utils: a formula that got inlined instead

`vk_utils.hpp` is the thin C++20 layer over Vulkan, and its reach is narrower than its surface: `vk_failed` and `vk_result_name` have one production call site each, both inside `gpu_allocator.cpp`, plus one assertion apiece in `tests/engine/engine_tests.cpp`; `vk_check` has neither. The helper that carries weight is `as_mapped_span`, which turns a persistently mapped `void*` into a typed `std::span` behind a `GpuPod` (trivially copyable, standard layout) constraint; its one route in is `GpuBuffer::mappedAs`, which no caller uses — the render world reads its mapped staging memory through the raw pointer from `getMappedData()`.

`mip_levels_for` needs a more careful verdict than "unused". Its integer shift loop has no production callers — only that same test file, which pins its 1×1 and 256×128 answers — but the identical quantity, $\lfloor \log_2 \max(w,h) \rfloor + 1$, is computed in floating point at both places that actually build mip chains, the bindless texture uploader and the bloom pass:

static_cast<uint32_t>(std::floor(std::log2(std::max(width, height)))) + 1 : 1;ohao/gpu/vulkan/bindless_texture_manager.cpp:726
EXPECT(mip_levels_for(256, 128) == 9u, "256 mips"); // 256→1 = 9 levelstests/engine/engine_tests.cpp:513

The function is unreachable from the renderer; the formula is not. Deleting the helper breaks the `engine_tests` build, and concluding that the engine does not compute mip counts would be wrong on top of that.

Key idea

The allocation model is split along who owns the lifetime. The render world's geometry, tables and staging go through `GpuAllocator`, device-local and written only by copies; everything else — render targets, texture images, acceleration-structure storage, binding tables, the light uniform buffer — is one hand-rolled `vkAllocateMemory` per resource, host-visible and permanently mapped for what the CPU rewrites each frame. Judge a change against whichever side of that line the resource sits on.

Contracts

  • Emissive proxies travel in the same light list as every other light and are appended after the regular ones; the raster array holds at most `MAX_LIGHTS`, so a full list drops proxies first. Setting the list again rebuilds both consumers' arrays.
  • Two light-type encodings coexist inside one loop: the source `LightKind` (Point, Directional, Spot, AreaRect, EmissiveProxy) and the shader type packed into `position.w` (directional 0, point 1, spot 2). The remap is right for the first three and silently folds AreaRect into spot; the shadow-caster test reads the source encoding where the rest of the loop reads the packed one. Any edit here must state which encoding it is in.
  • `MAX_LIGHTS` is 8 in four places: `render_scene_types.hpp` for the C++ side, the `#define` hard-coded into `deferred_lighting.frag` — the one shader that reads the buffer, whose comment points at `offscreen_renderer.hpp`, a file that does not exist — an `#ifndef`-guarded copy in `includes/common/constants.glsl`, and `includes/common/types.glsl`, which no shader includes. Change the C++ value without the lighting shader's and the uniform block silently truncates or overruns.
  • The light uniform buffer is one host-visible allocation per frame slot. `renderDeferred` writes only the current slot's buffer, after that slot's fence wait, and hands that buffer to the lighting pass, which binds it in the same slot's descriptor set. Writing any other slot's buffer races the frames still in flight.
  • Every buffer the render world holds is created `GpuOnly` or as a mapped staging buffer through its own `GpuAllocator`; anything it replaces goes through the retire queue, never an immediate `destroyBuffer`.
  • `GpuAllocator::createBuffer` and `destroyBuffer` must both account `allocation.getSize()`; crediting requested bytes on one side drifts unsigned `currentUsage` downward until a debit underflows it, and `shutdown()` reports the wrapped value as a leak.
  • The device-address flag on the VMA allocator requires the device to have enabled `bufferDeviceAddress`; an allocator built against a device without it tags every block with a flag the device cannot honour.
