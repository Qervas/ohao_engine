Two speeds: load-time registration, per-frame staging

`render::RenderScene` is the only place geometry, materials, instances and lights turn into GPU state, and it moves at two speeds. *Registration* — a mesh, its textures, its materials — is load-time work: it records into a private one-shot command buffer, submits, and drains the queue before it returns.

vkQueueWaitIdle(m_ctx.queue);ohao/render/scene/mesh_registry.cpp:113

*Edits* are frame-time work. `createInstance`, `updateInstance`, `destroyInstance` and `setLights` touch only host copies and mark entries dirty; nothing reaches the device until the next frame's command buffer calls `recordUpdates`, which stages the dirty rows through a host-visible buffer owned by that frame slot and records one copy per contiguous run.

void RenderScene::recordUpdates(VkCommandBuffer cmd, uint32_t frameSlot) {ohao/render/scene/render_scene.cpp:353

So moving a mesh uploads one 160-byte `InstanceGpu` and refits the TLAS; it stalls nothing, because the slot's fence has been waited and the device-local table is only ever written by copies recorded in the same command buffer that will read it. The deferred light UBO is the one exception: `updateLightBuffer` re-reads the light table's host copy once per deferred frame into that frame slot's persistently mapped buffer, with no staging at all. One buffer per slot, written after the slot's fence wait, is what makes the direct write safe.

LightUniformBuffer* VulkanRenderer::updateLightBuffer(uint32_t slot) {ohao/gpu/vulkan/buffer_setup.cpp:60
Key idea

Nothing in the render world is torn down and rebuilt. Growth is the only thing that replaces a buffer, and a replaced buffer waits `MAX_FRAMES_IN_FLIGHT` frames in a retire queue before it is destroyed, so the frame path never idles the device.

One arena per stream, mesh-local indices

Every registered mesh is appended to four shared buffers: a vertex arena, an index arena, a per-triangle material-slot stream and a mesh table of 16-byte `MeshGpu` entries. A mesh records its slice as element offsets — `vertexOffset`, `indexOffset`, `triangleSlotOffset` — not byte offsets. The whole registration travels in one staging buffer, laid out vertices, indices, slots, entry:

// One staging buffer for the whole registration: vertices | indices | slots | entry.ohao/render/scene/mesh_registry.cpp:181

An arena that is full is replaced by one sized at twice what is required, the old contents are copied across on the same command buffer, and the old buffer is pushed to the caller's retire list rather than destroyed.

const VkDeviceSize newCapacity = required * 2;ohao/render/scene/mesh_registry.cpp:73
retired.push_back(a.buf);ohao/render/scene/mesh_registry.cpp:84

The indices in the arena stay *mesh-local*: they are not biased by the running vertex offset as they are appended. The bias is applied by whoever reads them, and there are three readers that must agree. The rasteriser passes the mesh's `vertexOffset` as `vkCmdDrawIndexed`'s base-vertex argument and the instance slot as `firstInstance`; the cascaded shadow pass draws the same list with the same arguments but a 64-byte push constant, the cascade's view-projection, in place of the G-buffer's material slot.

vkCmdDrawIndexed(cmd, draw.indexCount, 1, draw.firstIndex, draw.vertexOffset, draw.slot);ohao/render/deferred/gbuffer_pass.cpp:154
static_assert(sizeof(ShadowPushConstant) == 64);ohao/render/deferred/csm_pass.hpp:105

The BLAS build gets the same offset as its `firstVertex`, with the buffer base and a byte offset for the mesh's slice:

mesh.vertexOffset); // arena indices are mesh-localohao/render/scene/mesh_registry.cpp:126

and the closest-hit shader adds it by hand when it fetches a triangle's corners:

uint i0 = mesh.vertexOffset + idx[baseIdx + 0u];shaders/rt/pt_closesthit.rchit:63

The coupling is the point. Three consumers each apply the bias in their own idiom, and a change to how indices are stored — biasing at upload, say — would be correct for none of them until all three were edited, and wrong for any one left behind.

Geometry that is raster input, RT input and a storage buffer at once

The arenas are device-local, created `GpuOnly` and never mapped. Their usage mask is what lets one buffer serve every reader: it is a vertex or index buffer for the raster passes, a storage buffer for the hit shaders, and acceleration-structure build input with a device address for the BLAS builder.

VK_BUFFER_USAGE_ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY_BIT_KHR;ohao/render/scene/mesh_registry.cpp:21
Why

A mesh is resident once. The textbook layout keeps a raster vertex buffer and a separate device-local copy for ray tracing — two allocations per mesh and a re-upload whenever either changes. A shared arena pays instead in growth: when a stream fills, the whole arena is copied into a larger one. Built BLASes survive that, because a BLAS built without the update flag does not reference its inputs after the build. What it gives up is per-mesh release: arenas only append, so a mesh's range is not reclaimed while the scene lives.

Textures are uploaded into a description, not into the scene

`uploadModel` is the single entry point that turns a loaded `Model` into render-world state. It registers the mesh (one BLAS), pushes each material's maps into the bindless manager, and registers one `MaterialDesc` per material. The texture indices come back into the descriptions it is about to register; no scene object is mutated, and the returned `UploadedModel` is the only record of what was created. Materials come from the model's `materialColors` — one per entry — with scalar roughness read from the colour's `w` and metallic from the parallel array, falling back to `0.0f` when that array is shorter:

mats[i].metallic = i < model.materialMetallic.size() ? model.materialMetallic[i] : 0.0f;ohao/render/scene/model_upload.cpp:207

A model with no `materialColors` gets a single material: the caller's override, or the default. A material that loaded an emissive map is marked emissive with a flat strength; the strength does not scale with the map.

if (m.emissiveTex != kNoTexture) m.emissiveStrength = 1.0f;ohao/render/scene/model_upload.cpp:211

Submeshes are the contiguous runs of equal `materialPerTriangle` entries, capped at the triangle count; triangles past the end of that list use material 0. Each run becomes one draw.

The rough/metal branch carries a comment describing a repack and performs a copy: R to R, G to G, B to B, alpha forced to 255.

repacked[p * 4 + 1] = td.pixels[p * 4 + 1];ohao/render/scene/model_upload.cpp:66

An identity copy with an opacity fix. Not wrong — the layout it documents (R=AO, G=roughness, B=metallic) is the one the source already has — but the loop is the only thing implying a conversion happens.

Nothing deduplicates textures: each material uploads its own images, so a model whose materials share a pooled image uploads it once per material. Each upload takes a slot out of the manager's fixed table of 4096, and none is released while the scene lives.

An emissive texture, promoted to a light

A model that declares an emissive texture may have a light synthesised for it, with the intensity derived by reading the texture on the CPU. Write $R_p, G_p, B_p$ for a texel's channels in $[0,1]$, $Y(p)$ for Rec. 709 relative luminance, $S$ for the texels bright enough to count and $P$ for their summed luminance:

$$ Y(p) = 0.2126\,R_p + 0.7152\,G_p + 0.0722\,B_p, \qquad S = \{\,p : Y(p) > 0.05\,\}, \qquad P = \sum_{p \in S} Y(p) $$
$$ I = \min(0.1\,P,\;20), \qquad c = \frac{1}{|S|}\sum_{p \in S}\big(R_p, G_p, B_p\big) $$

Two gates decide whether the light exists at all, and neither is the per-texel $Y(p) > 0.05$ that defines $S$. The first is $P > 0.1$ on the whole texture: below it the scan runs, costs a full texture read, and produces nothing.

if (totalPower > 0.1f) {ohao/render/scene/model_upload.cpp:130

The second is a return at the foot of the per-material loop, placed *outside* the power test, so only the first material carrying a non-negative emissive index is ever examined. A model whose second material is the real emitter gets nothing.

return std::nullopt; // one light per model: only the first emissive material countsohao/render/scene/model_upload.cpp:138

The colour $c$ is a *mean* over $S$ and is independent of texture resolution. The intensity $I$ is a *sum* and is not: the same emitter authored at 2K instead of 1K feeds roughly four times the power into the same formula, and shifts the $P > 0.1$ gate by the same factor. The clamp at 20 hides the intensity half of that for most textures; nothing hides the gate.

light.intensity = std::min(totalPower * 0.1f, 20.0f);ohao/render/scene/model_upload.cpp:135

The light's geometry is half model space and half not. The proxy carries a model-space centre — the midpoint of the vertex bounding box — and a radius of 0.3 times the model-space diagonal.

const float radius = glm::length(bmax - bmin) * 0.3f;ohao/render/scene/model_upload.cpp:104

When the render extract resolves it into a world-space light, the centre goes through the entity's world matrix and the radius does not:

d.position = glm::vec3(wt.world * glm::vec4(p.localCenter, 1.0f));ohao/ecs/render_extract.cpp:170

Scaling an emissive entity moves its light correctly and leaves its size behind. The proxy is not a GPU upload by itself: it becomes an `EmissiveProxyLight` component, then a `LightDesc` of a special kind that the light table lowers twice — into the deferred `LightData` array after the regular lights, as a point light with a range of ten radii,

light.direction = glm::vec4(0, -1, 0, d.radius * 10.0f);ohao/render/scene/light_table.cpp:171

and into the path tracer's `GPULight` buffer as a sphere light.

The HDRI is its own upload

The environment map has nothing to do with lights except that its bindless index rides in the light buffer's 16-byte header, alongside the light count and an intensity scale. The upload does not run inside the light path: `render()` runs it once per requested path, before choosing a frame body, and drains the device first when a different panorama is about to join the bindless table.

if (!m_envMapPath.empty() && m_envMapPath != m_envMapLoadedPath) vkDeviceWaitIdle(m_device);ohao/gpu/vulkan/renderer.cpp:276

A scene with no lights and no emissive meshes therefore still gets its environment map: `env_demo --lighting=none` loads the HDR and creates no light at all, and the HDRI is still sampled by the path tracer's miss shader and the deferred sky reflections.

// LightingMode::None → no lights, HDR env IBL only (pure environment)examples/env_demo.cpp:389

The loader is guarded by a path cache: when the requested path matches the one already loaded, the function skips the decode and the CDF build and only re-stamps the index and the scale into the render scene. Without it every call would re-decode and re-upload a multi-megabyte HDR, so a caller that changed the path every frame would turn a scene-load cost into a per-frame one.

float* hdrPixels = stbi_loadf(m_envMapPath.c_str(), &ew, &eh, &ec, 4);ohao/gpu/vulkan/env_upload.cpp:49

The image is `R32G32B32A32_SFLOAT` — 16 bytes per texel, so a 4096×2048 panorama is 128 MB resident plus an equal host staging buffer.

imgInfo.format = VK_FORMAT_R32G32B32A32_SFLOAT;ohao/gpu/vulkan/env_upload.cpp:62

The renderer owns the image and its memory and frees them in one place, `destroyEnvMapImage`, at shutdown and before loading a different panorama; the view belongs to the bindless table once registered. The replacement path idles the graphics queue first, because frames still in flight may be sampling the old image.

// Replacing an earlier env map: frames in flight may still sample it.ohao/gpu/vulkan/env_upload.cpp:53

The last step hands the render scene the slot to stamp into its light header, or the no-texture sentinel when nothing loaded:

m_renderScene->setEnvMapTextureIndex(envMapLoaded() ? m_envMapTexIdx : render::kNoTexture);ohao/gpu/vulkan/env_upload.cpp:253

Contracts

  • Mesh indices are arena-local. Every reader applies `MeshInfo::vertexOffset` itself — as `vkCmdDrawIndexed`'s base vertex, as the BLAS `firstVertex`, and as an addend in the hit shaders. Change how one reads them and the other two silently break.
  • Offsets in `MeshInfo` and `MeshGpu` are element counts, not bytes; byte offsets are computed at the point of use.
  • `registerMesh` blocks on the queue and belongs to load time. Per-frame changes go through `createInstance`/`updateInstance`/`destroyInstance`/`setLights` and reach the device in `recordUpdates`.
  • A replaced arena or table buffer is retired, not destroyed; it is freed `MAX_FRAMES_IN_FLIGHT` frames later by `onFrameRetired`. Calling that tick more or less often than once per submitted frame breaks the lifetime guarantee.
  • `uploadModel` consumes slots in a 4096-entry bindless table and releases none; every upload of a model spends its materials' texture slots again.
  • The emissive proxy's centre is world-transformed and its radius is not.
  • The environment map reaches the GPU independent of lights. Its slot is stamped into the RT light header by `setEnvMapTextureIndex`, so loading a different path changes the header on the next frame.
