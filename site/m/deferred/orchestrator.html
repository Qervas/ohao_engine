A schedule written by hand, checked by a graph

Up to fourteen stages run per deferred frame, all recorded into one command buffer by `DeferredRenderer::render`. Eight go through `RenderGraph`; the rest go straight onto `cmd`. That split is most of the class, because the graph does far less than its name implies.

It does not schedule. `topologicalSort` copies passes into the execution list in `addPass` order and stops:

// Simple linear ordering for now (passes are added in correct order)ohao/render/graph/render_graph.cpp:579

So `csm` → `gbuffer` → `ssao` → `rt.shadows` → `rt.shadows.filter` → `rt.gi` → `rt.gi.denoise` → `lighting` (the pass registry's names, each timed under it except `gbuffer`, which the graph does not time: it times its own five parts, `cull.instances`, `gbuffer.early`, `hiz.build`, `cull.late` and `gbuffer.late`; `csm` only in frames where RT shadows do not run, `rt.shadows.filter` and `rt.gi.denoise` only in realtime quality, `ssao` only while the effect is on) is a decision made by hand in `render()`, not from declared dependencies. What the graph earns is barriers: `computeBarriers` walks that order tracking each texture's last access and emits a `VkImageMemoryBarrier` at the first read following a write.

declareColorWrite: a promise about a render pass the graph cannot see

Three of the eight are graphics passes — CSM, GBuffer, DeferredLighting — each owning its `VkRenderPass` and framebuffers, built before the graph existed; SSAO, the RT shadow trace and filter, and the RT GI trace and denoiser enter through `addComputePass` and own neither. The graph could take those render passes over, through `useColorAttachment`. It uses the other door:

// NOT added to colorAttachments — the pass manages its own VkRenderPassohao/render/graph/render_graph.cpp:155

`declareColorWrite` and `declareDepthWrite` record a `ResourceAccess` for barriers and withhold the attachment, so `vulkanRenderPass` stays `VK_NULL_HANDLE` and `execute` invokes the lambda with no render pass open around it — which is what lets the pass begin its own inside.

The price is an invariant nothing checks: the layout handed to `declare*Write` must be the `finalLayout` of the render pass the graph never sees. GBuffer declares `DEPTH_STENCIL_READ_ONLY_OPTIMAL` for depth, which has to match the depth attachment's final layout in the later of its two render passes:

a.finalLayout = late ? (depth ? VK_IMAGE_LAYOUT_DEPTH_STENCIL_READ_ONLY_OPTIMALohao/render/deferred/gbuffer_pass.cpp:554

Change it, forget the declaration, and nothing fails to build — the next barrier carries an `oldLayout` the image is not in. Of those five attachments only depth, normal and albedo are imported; position and velocity are outside the graph's tracking entirely.

Why

Letting the graph own attachments would mean redrawing every pass into graph-allocated images, trading hand-tuned load ops and subpass dependencies for barrier bookkeeping. Demoting it to a barrier calculator bought the missing shadow-map transition without touching CSM, GBuffer or lighting internals — at the cost of a declared layout kept in sync by discipline.

The layout the graph never learns

`PhysicalTexture::currentLayout` is written at import, reset to `UNDEFINED` by `reset()` each frame, and updated inside `execute` as barriers are issued — never during compilation. Since `compile()` runs `computeBarriers` first, every tracked texture reads as `UNDEFINED` while the barriers are computed.

That stays invisible on the anticipated path: a read following a *write* takes its `oldLayout` from the write's declared layout. A read following another *read* fails `isWrite()` and falls to the second branch, which sources `oldLayout` from the stale field and pairs it with `TOP_OF_PIPE` and an empty access mask:

// Transition from undefinedohao/render/graph/render_graph.cpp:628

`gbuffer_normal` is read by the first compute pass (`ssao` when the effect is on, else `rt.shadows`) and again by each pass after it, so the graph emits exactly that — after the write, immediately before lighting samples it. `UNDEFINED` licenses the driver to discard the contents, the source scope carries no dependency, and both are legal, so validation stays silent.

One layout per texture, so every layer moves

The CSM shadow map is a four-layer array, 2048 × 2048 per cascade, imported through `CSMPass::getShadowMapArrayView()`. `PhysicalTexture` tracks a single `currentLayout` per texture and has no notion of layers, so the only barrier consistent with that model is one that moves the whole image:

imageBarrier.subresourceRange.layerCount = VK_REMAINING_ARRAY_LAYERS;ohao/render/graph/render_graph.cpp:455

The `DEPTH_STENCIL_ATTACHMENT_OPTIMAL` → `SHADER_READ_ONLY_OPTIMAL` transition before deferred lighting therefore covers all four cascades the lighting shader samples through its array view. The mip range stays hardcoded to level 0, which is all any imported texture has today; a mipped import would need the same treatment.

frameIndex selects a descriptor set; the jitter has its own index

`render()` hands `frameIndex` — `VulkanRenderer`'s frame-in-flight slot, whose fence was waited before recording began — to every pass `execute` it calls. Its first job is to pick descriptor sets. Every pass whose inputs change between frames owns one set per slot and rewrites only that slot's set at record time: the G-buffer's scene set, GPU culling's set, CSM's table set, lighting, SSAO, SSS, SSR, TAA, bloom's input set and the tonemap. A single shared set rewritten every frame would be modified while up to two already-submitted frames still read it; the slot's set is the one whose previous reader the fence has retired.

std::array<VkDescriptorSet, MAX_FRAMES_IN_FLIGHT> m_descriptorSets{};ohao/render/deferred/deferred_lighting_pass.hpp:113

Sky and gizmo own no set or write theirs only at setup or when an input view changes, and leave the parameter commented out. The slot is not a frame counter: it wraps at `MAX_FRAMES_IN_FLIGHT` = 3, so anything that needs a sequence takes another index. TAA's jitter, read at the top of `render()` to perturb the projection, is the Halton sample of the frame's index since the last temporal reset:

glm::vec2 jitter = m_postProcessing ? m_postProcessing->getJitterOffset(m_framesSinceReset) : glm::vec2(0.0f);ohao/render/deferred/deferred_renderer.cpp:261

`TAAPass` builds 16 Halton (2, 3) samples and indexes them `frameIndex % 16`, so the sequence walks all sixteen and repeats. The slot would reach only samples 0, 1 and 2 (base-2 offsets $h_x \in \{0, -\tfrac14, +\tfrac14\}$), and would tie a capture's image to the slot its first frame happened to take. With the reset counter, frame *k* after a reset jitters the same way in every run.

Jitter goes into the matrix, not the camera:

jitteredProj[2][0] += jitter.x;ohao/render/deferred/deferred_renderer.cpp:263

GLM matrices are column-major, so `[2][0]` is the entry in row 0, column 2 — call it $P_{02}$. For a right-handed perspective $w_{\text{clip}} = -z_v$ and $P_{02} = 0$, so adding $j_x$ there gives, for a view-space point $(x_v, z_v)$:

$$ x_{\text{ndc}} = \frac{P_{00}\,x_v + j_x\,z_v}{-z_v} = -\frac{P_{00}\,x_v}{z_v} - j_x $$

The $z_v$ cancels: the shift is a constant $-j_x$ in NDC at every depth. The frustum is sheared, not the camera translated — near and far planes stay put, no parallax appears, only the sample grid moves.

The amount is off. NDC spans two units across $W$ pixels, so a shift of $j_x$ is $j_x W/2$ pixels; the jitter is a Halton offset $h_x \in [-0.5, 0.5)$ over $W$, landing as $h_x/2$ pixels — half the nominal sub-pixel step. The sixteen samples sweep 0.45 px in x and 0.43 px in y where a full pixel footprint would take nearly 1:

return m_jitterSequence[sampleIndex] / glm::vec2(m_width, m_height);ohao/render/deferred/taa_pass.cpp:183

The same jitter poisons motion vectors: the GBuffer gets `jitteredProj` while `m_prevViewProj` is stored unjittered at the end of `render()`, and `gbuffer.frag` writes velocity as half the NDC difference of the two — a screen-constant $-j_x/2$ UV bias that changes every frame.

The half of the frame the graph never sees

After `m_renderGraph.execute(cmd)` returns, sky, the effects' compute (`vfx.expand`, `vfx.sort`), SSS, SSR, the transparent pass, post-processing and gizmos are recorded directly, each rolling its own barriers. `SSSPass` blurs the skin tiles of the lit image *in place*, and SSR traces that same image at half resolution, so post-processing always reads the lighting output:

m_postProcessing->setHDRInputWithImage(m_lightingPass->getOutputView(), m_lightingPass->getOutputImage());ohao/render/deferred/deferred_renderer.cpp:658

The sky still comes first. It draws into the lighting image, and SSS's blur and SSR's reflections should see what it drew: an SSS pass recorded before the sky would blur skin edges against a black background, and SSR would reflect none. Without an environment, `core/deferred_lighting.slang` writes zero wherever the GBuffer position sample is exactly zero, and `sky.frag` fills whatever the GBuffer left at far depth (it discards every depth below the cleared 1.0), so the sky pass is the whole sky, and until it runs the background those taps and hits would read is black. With one, lighting writes the environment into those pixels itself, as the path tracer's missing camera rays see it:

o.color = float4(pc.envIntensity * envPrefiltered.SampleLevel(equirectUV(viewDir), 0.0).rgb, 1.0);shaders/core/deferred_lighting.slang:158

The sky writes through a render pass as a colour attachment, which no compute read is ordered against, so when it ran a memory barrier from colour-attachment output to the compute and fragment stages comes before SSS:

// Sky drew into the lit image as a color attachment; SSS (compute), SSR and post sampleohao/render/deferred/deferred_renderer.cpp:608

`onResize` keeps every screen-sized target at the output extent — the GBuffer, lighting, post, gizmo, sky, SSS, SSR and both RT techniques.

Ordering constraints that are not obvious

GPU culling has to begin the frame before any graph pass culls. `render()` calls `GpuCulling::beginFrame` just before compiling the graph: it binds `RenderScene`'s draw table to the slot's culling set, clears a stale visibility history, and makes sure the culling buffers hold every draw. Inside the graph, `csm` culls its four cascades before its render passes, and `gbuffer` culls its early and late phases around its two render passes; both draw indirectly from the lists that leaves.

if (m_culling && m_renderScene) (void)m_culling->beginFrame(cmd, frameIndex, *m_renderScene);ohao/render/deferred/deferred_renderer.cpp:539

The culling's Hi-Z pyramid is sized from the G-buffer's depth, so `onResize` resizes it right after the G-buffer, handing it the new depth view. The draw table it reads was uploaded by `RenderScene::recordUpdates` earlier in the same command buffer, as `scene.upload`.

Before compiling the graph, `render()` also clears the RT shadow visibility and the GI view out of the lighting pass. They come back only from inside the RT pass lambdas — the shadow visibility from `rt.shadows.filter` in realtime quality or from `rt.shadows` in reference, the GI view likewise from `rt.gi.denoise` in realtime or from `rt.gi` in reference — and only when that technique's `render()` actually traced:

if (m_lightingPass && m_rtGI->rendered())ohao/render/deferred/deferred_renderer.cpp:463

The hand-off happens at record time, during `m_renderGraph.execute(cmd)`, and its consumer is `DeferredLightingPass::execute` later in the same walk, which writes its slot's descriptor set from those members and re-derives the RT-shadow and SSGI flag bits from them. So the dependency is pure graph order: the RT passes must be added before `DeferredLighting`. Since `topologicalSort` keeps insertion order and the lighting pass declares no read of the RT outputs, nothing in the graph enforces it — move the RT blocks below lighting and every frame silently falls back to CSM and no GI.

m_params.flags |= 32; // RT shadows (bit 5)ohao/render/deferred/deferred_lighting_pass.cpp:186

Two clocks feed the passes, and neither depends on any pass running. `m_totalTime` advances by the frame's delta on every frame; the sky pass takes it as a star seed. The RT passes are seeded instead by a frame counter, `m_framesSinceReset`, taken once per `render()` and handed to both RT shadows and RT GI with the render seed; TAA's jitter reads the same counter before it advances:

const uint32_t rtFrame = m_framesSinceReset++;ohao/render/deferred/deferred_renderer.cpp:413

`resetTemporalState` zeroes both clocks and drops RT shadows', RT GI's, TAA's and GPU culling's history, so frame *k* after a reset traces the same rays, takes the same jitter and draws the same lists in every run with the same seed (the first frame's early pass draws nothing, its late pass everything visible). It records nothing and waits for nothing: it only marks state. The next frame's passes start without history: the RT techniques take none (each `resetHistory` drops a validity flag and the reference frame count), and TAA clears its images in that frame's own command buffer. TAA's clear of its two history images is ordered after the frames still in flight, which may write one (TAA's render pass) or sample one (TAA, the tonemap), by its barrier's source stages alone:

vkCmdPipelineBarrier(cmd, VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT | VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT,ohao/render/deferred/taa_pass.cpp:133

Commands on one queue are ordered by submission, so a barrier in a later submission waits for those stages of every earlier one; no device idle is needed.

Key idea

`RenderGraph` here is a barrier calculator, not a scheduler and not a resource manager. Pass order, lifetimes and every barrier outside the eight graph passes are hand-written.

Contracts

  • The layout passed to `declare*Write` must equal the `finalLayout` of that pass's own `VkRenderPass`, and a declaring pass must never also take a graph-owned attachment. Neither is validated.
  • A tracked texture read by two graph passes in a row gets a second barrier with `oldLayout = UNDEFINED` and `TOP_OF_PIPE` as its source: `currentLayout` is never refreshed during compilation.
  • `setRTShadowMask` and `setSSGITexture` must be called before `DeferredLightingPass::execute` records, which happens only if the RT passes are added to the graph ahead of lighting. A view handed over after lighting recorded is cleared again before the next frame's graph runs.
  • `frameIndex` must be the slot whose fence `VulkanRenderer` just waited: it selects the per-slot descriptor set each pass rewrites.
  • SSS blurs the lighting HDR image in place and SSR reads it, so anything drawn into it after them reaches the tonemapper but is neither blurred nor reflected. The sky is recorded before both for that reason, followed by the colour-attachment-to-compute barrier; the transparent pass (blended surfaces and effects) is recorded after SSR on purpose, so a reflection never shows what stands in front of the mirror. A new pass drawing into the lit image belongs in one of those two places.
  • `importGraphTextures()` must run after any pass reallocates its images, or the graph holds destroyed `VkImage` handles.
  • `frameIndex` is a ring index of period 3, not a monotonic counter. Anything that needs a sequence (TAA's jitter, the RT seeds) takes `m_framesSinceReset`.
  • `resetTemporalState` must stay free of GPU waits and recorded work. A pass that clears history images does it in its next `execute`, behind a barrier whose source stages cover every earlier frame's use of them.
