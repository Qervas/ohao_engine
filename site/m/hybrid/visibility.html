Eight bits between a ray and a triangle

Every TLAS instance in Vulkan carries an 8-bit `mask`, and every `traceRayEXT` call carries an 8-bit cull mask. When the two share no set bit the traverser drops the instance before any intersection test — no BLAS descent, no any-hit invocation, no shader cost. `rt_visibility.hpp` is the twenty-two lines that name those bits for OHAO, and it opens by stating the rule it is built on:

// Vulkan rule: ray intersects instance if (ray_mask & instance_mask) != 0.ohao/render/rt/rt_visibility.hpp:7

Writing that as a predicate makes the rest of this page checkable. Let $m_i$ be the instance mask that ends up in `VkAccelerationStructureInstanceKHR::mask`, and $m_r$ the cull mask passed as the third argument of `traceRayEXT`:

$$ \text{visible}(r,\,i) \iff (m_r \wedge m_i) \neq 0 $$

with $\wedge$ the bitwise AND over eight bits. The scheme the header sketches gives bit 0 the meaning "GI and shadow rays may see this," reserving bits 1–7 for ray classes that do not exist yet (reflection, AO). A ray that wants only rigid geometry passes $m_r = \texttt{0x01}$; geometry it must not see clears bit 0.

Only the ray-mask half is hybrid-specific. Every `traceRayEXT` in `pt_raygen.rgen`, `pt_raygen_offline.rgen` and `pt_raygen_realtime.rgen` passes `0xFF`, so the path tracers never cull by mask; `rt_shadow.rgen` and `rt_gi.rgen` are the only rays in the tree that pass anything else. The instance-mask half is *shared*: the `RenderScene` stamps the mask into every instance of its one TLAS, and that same TLAS is what the deferred renderer's RT passes and the path tracer both trace.

rtRenderer->setSceneBuffers(*m_renderScene);ohao/gpu/vulkan/render_dispatch.cpp:315

A bad instance mask is therefore not contained to the hybrid passes.

Two masks in use, five constants named

Read the five constants and the scheme collapses. Static geometry is `0xFF`, animated geometry is `0x00`:

constexpr uint32_t MASK_ANIMATED = 0x00; // TEST: completely invisible to ALL raysohao/render/rt/rt_visibility.hpp:16

`0x00` does not mean "invisible to GI rays." Under the predicate above it fails against *every* $m_r$, including the `0xFF` of the path tracer's primary trace — so in the *path-traced* image an instance carrying it is a hole in the frame, not a missing bounce. The `TEST:` prefix is the author flagging it as a diagnostic value. A production "animated" value would be something like `0xFE`: visible to camera rays, culled by anything that passes `0x01`.

The tree never assigns the named constants. Exactly two values reach a TLAS instance, chosen by visibility:

vi.mask = visible ? 0xFFu : 0u;ohao/render/scene/render_scene.cpp:102

A live, visible instance carries `0xFF`, bit-identical to `MASK_VISIBLE_ALL`; a hidden one, or a released slot that keeps its place in the table, carries zero. That is the `MASK_ANIMATED` behaviour used deliberately: a hidden instance is a hole in the path-traced image and casts no RT shadow and gives no GI bounce. The deferred frame agrees, because the rasteriser draws only the instances the `RenderScene` marks visible, so what the G-buffer shows and what the rays see cannot disagree.

Consequently $\texttt{0x01} \wedge \texttt{0xFF} = \texttt{0x01} \neq 0$ for every visible instance in every scene the engine can currently build: the shadow and GI rays that carefully pass `RAY_MASK_STATIC` cull nothing that is on screen. The static/animated distinction the header sketches is unused — there is no skeletal geometry in the RT path to separate — while the visible/hidden distinction it does not name is the one that is live.

Key idea

`MASK_STATIC_ONLY` and `MASK_VISIBLE_ALL` are the same number, and neither is referenced by any code. Reintroducing animated RT geometry means giving those instances a mask with bit 0 clear in the `RenderScene`'s instance stage — not merely starting to write `MASK_ANIMATED`. Add the new instance class alone and the `0x01` rays still hit it.

Four copies of one constant

The header is C++; the cull mask is consumed in GLSL. There is a mirror file that promises to keep the two in step:

// RT visibility masks — must match ohao/render/rt/rt_visibility.hppshaders/rt/includes/rt_masks.glsl:1

No shader includes it. `rt_gi.rgen` and `rt_shadow.rgen` each pull exactly one header, `includes/common/encoding.glsl`, and nothing else in `shaders/` names `rt_masks.glsl` at all. Both consumers instead hard-code the literal and point at the C++ header in a comment — the GI raygen:

uint rayMask = 0x01; // RT_RAY_MASK_STATIC (see rt_visibility.hpp)shaders/rt/rt_gi.rgen:84

and the shadow raygen, inline in the trace call. So `0x01` is written down in four places — the C++ `RAY_MASK_STATIC`, the uncompiled `RT_RAY_MASK_STATIC` macro, and one literal in each raygen — with no compiler or build step linking them, and the one file whose whole job is to prevent drift is dead. The C++ side is no better off: `render_dispatch.cpp` includes `rt_visibility.hpp` and references no symbol from it, and nothing else includes it, so no code uses any of its constants.

A hit shader that trusts the traversal

The hit shader does not second-guess the cull mask. `rt_gi.rchit` reads the instance's albedo from the `RenderScene` instance table at binding 6, indexed by the TLAS custom index (the instance slot), and returns it with the hit distance:

vec3 albedo = instances[gl_InstanceCustomIndexEXT].giAlbedoPacked.rgb;shaders/rt/rt_gi.rchit:19

There is no software re-implementation of the visibility test in it. Whether a ray may reach an instance is decided entirely in traversal — an `AND` of the raygen's `0x01` against the instance's `0xFF` or zero — at no per-hit shader cost, and a hit the traversal reports is always counted.

The consequence is that the mask is the only switch. A hidden instance is removed by its zero mask alone; there is no second, per-instance flag in the albedo data that could contradict it.

Four interfaces, two implementations

`render_technique.hpp` is the other half of this unit: a pluggable-technique contract for the hybrid passes. Each feature gets an `Input` struct of GBuffer views, camera matrices and a nullable `VkAccelerationStructureKHR`, an `Output` struct of one image plus its view, and a uniform lifecycle — `init / resize / render / getOutput / destroy`, plus `getName()` and `needsRT()` for introspection. Four interfaces are declared: shadows, GI, reflections, AO.

Two have implementations. `RTShadowTechnique` and `RTGITechnique` are the only classes in the tree deriving from any of them; `IReflectionTechnique` and `IAOTechnique` have zero implementers. The screen-space features that would fit those two slots do exist, but on a different base — `SSRPass` and `SSAOPass` both derive from `RenderPassBase`, the base the rest of the deferred pipeline uses, and from none of the four interfaces:

class SSAOPass : public RenderPassBase {ohao/render/deferred/ssao_pass.hpp:8

The `Output` doc comments have drifted too — `ShadowOutput::shadowMask` is annotated "R8 or R16F" —

VkImage shadowMask; // R8 or R16F — 0=shadowed, 1=litohao/render/rt/render_technique.hpp:49

— while the implementation commits to a single format, `VK_FORMAT_R8_UNORM`, and `GIOutput::indirectLight` is documented RGB16F but allocated RGBA16F.

imageInfo.format = VK_FORMAT_R8_UNORM;ohao/render/rt/rt_shadow_technique.cpp:104

The runtime swap that is not wired

The header's premise is polymorphic substitution, stated in its own example:

// Swap at runtime: renderer.setShadowTechnique(std::make_unique<RTShadows>());ohao/render/rt/render_technique.hpp:13

No such setter exists anywhere in the tree. `DeferredRenderer` owns the techniques by *concrete* type, not by interface pointer:

std::unique_ptr<RTShadowTechnique> m_rtShadow;ohao/render/deferred/deferred_renderer.hpp:142

and `getName()` / `needsRT()` are overridden but never called. The virtual dispatch is therefore paid for and unused: the vtable exists, the indirection happens, and the pointer is always the same derived type. What actually varies at runtime is coarser — `init()` returning false makes the renderer drop the technique and fall back to CSM shadows, a boolean choice, not a technique swap.

Why

`rt_meta.hpp` hedges this by writing the same surface down a second time, as a C++20 concept: {{cite ohao/render/rt/rt_meta.hpp "concept ShadowTechniqueLike = requires(T t, VkCommandBuffer cmd, const ShadowInput& in,"}} The assertion that binds concept to implementation cannot live in `rt_meta.hpp` — the include edge runs the other way, `rt_shadow_technique.hpp` and `rt_gi_technique.hpp` both include it — so each derived header asserts against itself, one line below the class it just closed: {{cite ohao/render/rt/rt_shadow_technique.hpp "static_assert(ShadowTechniqueLike<RTShadowTechnique>);"}} So the shape is checked structurally as well as virtually, and that is the escape hatch: once the virtual bases go, `template<ShadowTechniqueLike T>` keeps the same guarantee with no vtable. The rejected alternative — deleting the interfaces outright — throws away the documented shape that both implementations and the fallback logic already agree on. The two variable templates the concepts also constrain carry none of that weight: {{cite ohao/render/rt/rt_meta.hpp "inline constexpr bool kIsShadowTechnique = true;"}} A constrained variable template is only checked when instantiated, and neither `kIsShadowTechnique` nor `kIsGITechnique` is instantiated anywhere in the tree. The `static_assert`s are the whole of the enforcement.

The handover the graph does not see

The RT techniques record into the render graph as compute passes, but their outputs reach the deferred lighting pass through a CPU-side member write, not a graph edge. Before the graph executes, the renderer clears both inputs, so lighting falls back to CSM shadows and no indirect light unless something hands them over:

m_lightingPass->setRTShadowMask(VK_NULL_HANDLE, VK_NULL_HANDLE);ohao/render/deferred/deferred_renderer.cpp:412

Each RT pass's record callback then hands its view over — but only if its `render()` actually dispatched, which it does not without a TLAS:

if (m_rtShadow->rendered() && m_lightingPass)ohao/render/deferred/deferred_renderer.cpp:338

The lighting pass reads those members at its own record time, when it rewrites this frame slot's descriptor set and picks its flag bits: RT shadow mask if one arrived, CSM otherwise. So a frame samples exactly what that frame traced, and any image a technique reallocates is re-bound on the next frame because the handover repeats every frame.

What makes it work is ordering, not tracking. The graph records passes in the order they were added:

// Simple linear ordering for now (passes are added in correct order)ohao/render/graph/render_graph.cpp:576

and `RTShadow` and `RTGI` are added before `DeferredLighting`. Register a technique after the lighting pass, or give the graph a scheduler that reorders passes, and lighting records before the handover and silently takes the fallback.

The resize path forwards the new extent to both RT techniques, because each owns a screen-sized target:

if (m_rtGI) m_rtGI->resize(width, height);ohao/render/deferred/deferred_renderer.cpp:577
if (m_rtShadow) m_rtShadow->resize(width, height);ohao/render/deferred/deferred_renderer.cpp:576

`RTShadowTechnique::resize` destroys the view, image and memory and reallocates at the new extent:

void RTShadowTechnique::resize(uint32_t width, uint32_t height) {ohao/render/rt/rt_shadow_technique.cpp:541

That is what keeps the mask registered with the dispatch grid, which takes its extent from `ShadowInput`, set from the renderer's current `m_width`/`m_height`:

input.width, input.height, 1);ohao/render/rt/rt_shadow_technique.cpp:523

A technique left at its `init()` extent would launch more threads than the image has texels after the window grows; the out-of-range `imageStore`s are discarded and the lighting pass samples an old-extent mask with normalized coordinates, stretched over the whole frame. The per-frame handover keeps the handle valid — it cannot fix the resolution.

Contracts

  • Instance mask and ray mask must be non-disjoint or the instance is invisible: `(m_r & m_i) != 0`. `MASK_ANIMATED = 0x00` is disjoint with *everything*, including the `0xFF` the path tracer's primary trace passes, so it removes geometry from the path-traced image outright — a debugging value, not the production animated mask.
  • Instance masks are written once, by the `RenderScene`, into the one TLAS both the deferred renderer and the path tracer consume. A mask change is not scoped to the hybrid passes.
  • Visible instances carry `0xFF` and hidden ones zero, so `RAY_MASK_STATIC` culls only hidden geometry. Any future animated-geometry class must clear a bit in the *visible* mask, not just define a new constant.
  • `0x01` exists as the C++ `RAY_MASK_STATIC`, as the uncompiled `RT_RAY_MASK_STATIC` macro in `rt_masks.glsl`, and as a hard-coded literal in each of `rt_gi.rgen` and `rt_shadow.rgen` — four sites. Changing the header does not change the shaders.
  • `rt_gi.rchit` filters nothing: the cull is the ray mask against the instance mask alone, and the closest-hit returns `giAlbedoPacked.rgb` of whatever slot traversal reports.
  • Technique outputs reach the lighting pass only through the per-frame handover in each RT pass's callback, and only when `rendered()` is true. The graph does not track this dependency; it holds because the RT passes are added before `DeferredLighting` and the graph records in insertion order.
  • `DeferredRenderer::onResize` must forward the new extent to every RT technique it owns. It forwards to both `m_rtGI` and `m_rtShadow`; a technique added without a forward keeps its `init()` extent while the dispatch grid follows the window.
  • `init()` failure is non-fatal by design — the renderer resets the `unique_ptr` and continues on the CSM path, so a null `m_rtShadow` is a valid steady state, not an error.
