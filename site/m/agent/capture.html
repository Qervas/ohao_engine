What an agent looks at

`render.capture` is how an agent sees the world: a PNG file, an inline preview image, or both. The session checks the whole request (path, mode, sizes, post effects, exposure, region) and then hands it to its `api::Host`. Two hosts implement it. One is the CLI's headless `host::RenderHost`, used by `ohao run --render` and headless `ohao serve`, which starts a renderer on first capture. The other is the window's `runtime::LiveHost`. Both end in one procedure, `runtime::captureFrame`. It applies the world's camera and environment, sets the mode, denoiser, post effects and exposure, does a temporal reset, renders `frames` frames each after `World::sync()`, and reads back the last one. The CLI unit describes the frame defaults and the reset. This unit covers the parts sub-project 4 added: readback on request, what a window may capture, and the image encoders.

Because the procedure is shared, a lockstep window capture and a headless capture of the same world at the same size are the same pixels by construction, not by a tolerance. `check_live.py` compares them byte for byte, with post effects off and on.

Readback on request

A capture asks for its last frame and gets that frame. Every reader of pixels works this way (captures, the examples, the tests, `ohao doctor`), and no frame copies anything to the CPU unless it was asked for, headless or windowed. `requestReadback()` marks the next frame, and cancels a preview request made before it:

void requestReadback() noexcept {ohao/gpu/vulkan/renderer.hpp:132

The flag is consumed by the next frame that starts, whether or not that frame is actually rendered:

// A request belongs to this frame; a frame that is not rendered leaves no readback.ohao/gpu/vulkan/render_dispatch.cpp:96

A frame skipped because the window is minimized or the swapchain is out of date leaves nothing to read, and `readback()` returns an empty span instead of an old frame. When the frame did copy, `readback()` waits on that frame's fence only, never on the queue or the device, and returns a view of the slot's persistently mapped buffer:

const std::size_t bytes = static_cast<std::size_t>(m_width) * m_height * 4;ohao/gpu/vulkan/render_dispatch.cpp:84

In a window the copy is recorded inside the swapchain blit, where the final image is already in `TRANSFER_SRC` layout, so it costs one extra copy command and no layout transitions:

// A requested readback: the same image, already a transfer source, into theohao/gpu/vulkan/render_dispatch.cpp:278

A headless frame copies the same way, only when asked (`copyDeferredOutputToStaging`). The renderer counts the copies (`requestedReadbackCount()`); the window host counts its own requests beside them. The presentation gate (`ohao_game --frames N`), `check_live.py` and `e2e_mcp.py` all require the difference, the unrequested copies, to stay 0 through teardown.

return copies > m_readbackRequests ? copies - m_readbackRequests : 0;ohao/runtime/live_host.cpp:232

The CPU reads the staging buffers, so they are allocated host-cached where the device offers cached memory that is also coherent:

// Readback buffers: the CPU reads them, so host-cached memory where the device offers itohao/render/frame/frame_resources.cpp:174

Reading one 1280x720 frame (3.7 MB) from uncached host-visible memory took about 20 ms. The spec's sub-project 4 step-9 note records a one-frame headless capture dropping from about 45 ms of CPU time to about 1 ms.

A path-traced capture under a CPU-side denoiser (OIDN, NRD) reads the same way. `readback()` denoises the requested frame's images itself, once its fence has signalled:

const std::span<const uint8_t> pixels = renderer.readback(); // a CPU denoiser runs in hereohao/runtime/frame_capture.cpp:139

What a window may capture

`LiveHost::capture` refuses a few requests before rendering anything. A minimized window has no frame (`E_STATE`). Another size is `E_COMMAND`: the window captures at its own size, and the agent leaves `width` and `height` out. A path-traced mode on a GPU without ray tracing is `E_COMMAND` too:

out.errors.push_back(error("E_COMMAND", "this GPU has no ray tracing: a window host captures deferred frames only"));ohao/runtime/live_host.cpp:314

Otherwise the result depends on the time mode. In lockstep (or paused), the host first renders once if a resize is still pending, so the capture is at the window's current size. It then saves the window's post settings, quality, denoiser and mode, runs `captureFrame` with a reset every time in the requested mode, and restores them all, leaving the capture's last frame on screen. Every frame of the capture is presented, so a path-traced capture's sample passes converge on screen while the agent waits. In realtime the world is moving, and a reset or extra frames would show the agent something the player never saw. So the capture is the next frame the window presents, with the live settings, and in the mode the window presents (its `--mode`); another mode is `E_COMMAND`:

// Realtime: the next frame the window presents, as is (no reset, the live settings),ohao/runtime/live_host.cpp:323

A lockstep capture checks the call's cancel flag between whole frames and reports progress after each one (the server sends it at most every 250 ms). A cancelled capture reads nothing back and gets no answer, and the window returns to its live mode:

if (i > 0 && control && control->cancel && control->cancel->load(std::memory_order_relaxed)) {ohao/runtime/frame_capture.cpp:228

That result is marked `deterministic: false`. A lockstep capture of the same world always gives the same pixels. That holds after step 1 of the sub-project, which made every deferred configuration bit-identical run to run (see the hash and determinism unit).

Region, preview and the image beside the result

`region: [x, y, w, h]` crops the frame before anything else, so an agent can zoom into a detail at full resolution without paying for the whole frame. A region outside the frame is `E_COMMAND` at `/region`. The crop then goes to the PNG file (`path`) if one was asked for, and to the preview (`inline: true`). The preview is scaled so its long side is at most `maxSize`, 768 px by default; the spec puts a 768x432 preview at about 440 tokens. The scale is an area average: each output pixel is the mean of the source pixels it covers, each weighted by how much of it falls inside:

const double cover = std::min<double>(b, k + 1) - std::max<double>(a, k);ohao/runtime/image.cpp:44

`fitWithin` resamples vertically first, so each output row is a weighted sum of whole source rows, a run of contiguous multiply-adds per tap, and then horizontally over only the rows that are left. The spec measures 3 ms for 1280x720 to 768x432. The preview is a JPEG at quality 85 through `stb_image_write` (about 3.5 ms for 768x432), or a PNG when `format: "png"` asks for exact pixels.

That CPU path serves a capture that writes a file, keeps the whole frame, or renders in a path-traced mode. A deferred capture that wants the inline image and nothing else gets its preview from the GPU instead (next section), filtered the same way.

capture.preview: the preview made in the frame

An inline-only capture has no use for the full frame on the CPU, so it does not read it. `requestCaptureReadback` decides which request the last frame carries: the preview alone when the request is inline, names no `path`, the caller keeps no pixels, and the renderer can make it; the whole frame otherwise.

if (!r.inlineImage || !r.path.empty() || needPixels || !renderer.previewOnGpu()) {ohao/runtime/frame_capture.cpp:79

The rectangle is the `region` or the whole frame, and the long-side limit is `maxSize`. `renderDeferred` records the pass after the deferred passes and the gizmo, before the present blit or the headless copy, as `capture.preview` in the pass registry. `CapturePreviewPass` binds the final RGBA8 image as a sampled image and the frame slot's staging buffer as a storage buffer, and dispatches one thread per preview pixel. Its output goes straight into the host-cached buffer the CPU reads, packed, rows top down; the frame copies nothing else, and `readbackPreview()` returns a view of it with its width and height. `readback()` on that frame returns nothing.

vkCmdDispatch(cmd, (dstWidth + 63) / 64, dstHeight, 1); // rows of 64 (the shader's workgroup)ohao/render/deferred/capture_preview_pass.cpp:93

The preview's size comes from one function, `render::previewExtent`, which `fitWithin` calls too, so the GPU and CPU previews of one rectangle always have the same dimensions: the long side scaled to `maxSide`, aspect kept, each side rounded and at least 1, and a source that already fits left as it is.

if (maxSide == 0 || longSide <= maxSide) return {width, height};ohao/render/frame/preview_extent.hpp:15

The shader is `fitWithin`'s filter. Each output pixel's footprint in x and y is $[i\,s/d,\,(i+1)\,s/d)$ for a source of $s$ pixels scaled to $d$; every source pixel it touches is weighted by the length of its overlap with the footprint, divided by the footprint's width, and the vertical sum is taken first. The UNORM texel is turned back into its byte before it is weighted, as the CPU filter reads bytes:

const float4 texel = round(finalImage.Load(int3(int2(pc.src.xy + uint2(x, y)), 0)) * 255.0);shaders/compute/capture_preview.slang:52

The workgroup is one row of 64 threads, so a warp's 32 four-byte writes are 128 contiguous bytes of host memory. An 8x8 tile spreads the same warp over four rows, four separate runs of 32 bytes. At 768x432 on the RTX 5070 Laptop GPU the 8x8 version took 0.49 ms and rows of 64 take 0.056 ms.

[numthreads(64, 1, 1)]shaders/compute/capture_preview.slang:39

Its push constants are `PreviewPush` in `shaders/shared/layout.json`: the source rectangle and the preview's size. One barrier orders the final image's writers (tonemap's or lighting's render pass, the gizmo) before the filter reads it, and one makes the shader's writes visible to the host, available once the frame's fence signals. `sp2b_s10_gpu_preview_matches_the_cpu_downscale` compares the GPU preview with `fitWithin` on the same frame and allows 1 for float rounding. It measured max_abs 0 at 1280x720 to 768x432, a 500x300 region to 200x120, and 1920x1080 to 768x432, and requires exact bytes at 160x120, which is not scaled. `sp2b_s10_a_preview_request_reads_back_only_the_preview` checks that the preview frame runs the pass, makes no full copy, and returns 768x432 RGBA8 (1.3 MB instead of 3.7 MB).

Without the pipeline (the renderer logs a warning at start-up) or in an RT mode, `previewOnGpu()` is false and inline captures take the CPU path, with the same result.

The reset and the frames ahead

A capture after the first resets the renderer's temporal state. In Deferred, `resetAccumulation` waits for nothing. It marks the next frame to start without history and returns; TAA clears its history images in that frame's command buffer, ordered after the frames still in flight by the queue (the deferred orchestrator unit covers the barrier).

// the frames in flight by the queue alone. Nothing here waits for the GPU.ohao/gpu/vulkan/renderer.cpp:520

So when the capture's last frame is submitted, up to two earlier frames may still be on the GPU, and the read frame waits for them anyway by queue order. `readCaptureOutputs` first waits for the frames submitted before the read frame, using the count `framesSubmitted()` gave before its `render()`, and starts the `readbackMs` clock after that. `readbackMs` is then the read frame's own fence wait and copy, not the frames queued ahead of it, which are logged at debug level instead.

renderer.waitForSubmitted(framesBefore);ohao/runtime/frame_capture.cpp:113

The window's realtime capture uses the same two functions, `requestCaptureReadback` and `readCaptureOutputs`, around its one presented frame. It checks the region against the window's size before rendering; a frame that reached no staging buffer (minimized, an out-of-date swapchain) is `E_STATE`.

The encoded preview does not go into the result JSON. It travels beside it, as `api::CallOutcome::image`. Over MCP it becomes an `image` content block after the text block, which is the form a model can look at:

if (!failed && o.image) { // render.capture inline: the image a model looks atohao/rpc/server.cpp:583

Over native JSON-RPC, and through `Session::call(string)`, it is appended to the result as `"image"` (base64) and `"mimeType"`. The result itself reports `width`, `height`, `imageSize`, `frames`, the total `ms`, `readbackMs` (the read frame's fence wait and copy, after the frames queued ahead of it have finished) and `encodeMs` (crop, scale, file and preview), plus the validation message count when the layers are on.

A PNG writer of its own

The spec planned `stb_image_write` for PNG files and named `fpng` as the fallback if the encode was over budget. It was over by two orders of magnitude:

// stb_image_write's PNG took 7.3 s for one 1280x720 Cornell frame (its deflate tries up toohao/runtime/image.cpp:57

The budget for a whole PNG capture is 30 ms. `fpng` would have needed the network and a new dependency, so the ruling (ledgered in the spec) was a writer in `ohao/runtime/image.cpp`, designed around what rendered frames look like. Each row is filtered `Up`, meaning minus the row above it (the first row uses `Sub`). Flat and slowly varying regions, which a rendered frame has a lot of, filter to long runs of equal bytes. The filtered bytes are then deflated with the fixed Huffman codes and one kind of match only, a repeat of the previous byte:

if (run >= 3) { // a match at distance 1: the byte again, `run` timesohao/runtime/image.cpp:237

There is no hash chain, no search and no lazy matching: one pass, a byte compare per byte, and table lookups. The image is cut into bands of rows, each deflated on its own thread. The band count depends on the image height and never on the machine, so the file's bytes depend on the image alone:

const uint32_t bands = std::max<uint32_t>(1, std::min<uint32_t>(4, height / 64));ohao/runtime/image.cpp:277

The bands are joined the way pigz joins its blocks. Every band but the last ends with an empty stored block, which pads it to a byte boundary, so the bands' bytes can be concatenated:

if (!last) put(0, 3); // an empty stored block (BFINAL 0, BTYPE 00): aligns the bandohao/runtime/image.cpp:243

The zlib trailer's Adler-32 is combined from the bands' checksums with zlib's `adler32_combine` formula, so no thread has to read another band's data. One case defeats run-length coding: a one-frame RT GI render is mostly noise, which codes at about 8.5 bits a byte. For such a band, the writer falls back to stored blocks of raw bytes whenever they are smaller:

if (band.zn > n + blocks * 5) {ohao/runtime/image.cpp:258

On synthetic 1280x720 frames the spec measures 4.1 ms for a mixed image and 6.1 ms for pure noise. The files are larger than a full deflate would write. That is the trade: a capture file exists to be read back exactly, not archived. `sp4_t16_capture_png_round_trips_losslessly` decodes the output with `stb_image` and requires every byte back.

Where the time goes

A clean `serve_bench` run (step 11) puts a 1280x720 PNG capture at 22.7 ms against its 30 ms budget, a window readback at 5.34 ms against 2 ms, and an inline capture at 34.3 ms against 20 ms. The record attributes both misses to the deferred frame's own GPU cost: one Cornell deferred 1280x720 frame takes 5.0 to 5.6 ms of GPU time, which a capture waits for. Frank ruled that both budgets stay exactly as they are and that the misses belong to sub-project 2b, which makes the frame cheaper. They are not to be closed by changing the budgets.

Why

Readback on request, rather than a ring that is always copying, makes "the frame I just rendered" a direct question. The capture marks its last frame, waits for that frame's fence, and reads the copy, with no lag to compensate for and no guessing at `+3`. It also keeps a presenting window free of transfers: a frame that nobody captures never touches the staging buffer, and the gates check exactly that.

Key idea

One capture procedure serves both hosts, so a lockstep window capture equals a headless one bit for bit in deferred. The renderer copies a frame only on request, and the capture waits for that frame's fence alone, reading host-cached staging memory. A window host captures any mode in lockstep and its live mode in realtime, always at its own size; a path-traced lockstep window capture equals the headless one too (test 11, max_abs 0 measured). Previews are area-downscaled JPEGs that travel beside the result; an inline-only deferred capture has the GPU make the preview in the frame (`capture.preview`) and reads back only that. PNG files use a one-pass, four-band, run-length deflate.

Contracts

  • Call `requestReadback()` before the `render()` whose pixels you want, and `readback()` after it. The span is valid until the next `render()` or `resize()`.
  • `readback()` returns an empty span for a frame that was not rendered, and for a frame that served a preview request. Callers check the size before using it.
  • The GPU and CPU previews size themselves through `render::previewExtent` alone, and filter the same way; a change to one filter is a change to both, and `sp2b_s10_gpu_preview_matches_the_cpu_downscale` holds them together.
  • Call `readCaptureOutputs` right after the read frame's `render()`, with `framesSubmitted()` as it was before that `render()`.
  • The PNG writer's output depends only on the image. Its band count must never follow the core count.
  • A window host restores its live post settings after a lockstep capture. A capture never changes what the player sees afterwards.
