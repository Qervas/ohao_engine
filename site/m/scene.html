Scene & ECS

Chapter contract

How a world is represented before Vulkan, and how it reaches the GPU: the ECS World, transform propagation, the render extract, the persistent RenderScene, and the asset loaders that feed both. After this, "scene" is not a vague bag of meshes.

On this page

  2. Registry to GPU
  3. Asset load workflow

World lifecycle

From construction to a rendered frame
  1. World owns an EnTT registry and an ordered system list; the constructor installs the transform system first
  2. installRenderExtract inserts render_extract right after it and binds the world to a RenderScene
  3. Loaders and game code call World::create (every entity gets Name, Transform, Children, TransformDirty, CreationOrder) and attach MeshRenderer / Light
  4. Each World::update(dt) runs the systems in order: transforms settle and propagate, then the extract mirrors changes into the RenderScene
  5. The renderer calls recordUpdates at the start of its command buffer; the world is dropped before the renderer so the extract can release its slots

Edits must go through patch / replace so EnTT's update signals fire; a write through a plain get<>() reference is invisible to the dirty tracking, and verifyTransforms detects such writes for Transform. The hierarchy is stored in both directions, setParent rejects cycles, and destroy removes a whole subtree.

Registry to GPU

Three stages, each with one job.

  • Transform system - parent-first world matrices without sorting; keeps prevWorld for motion vectors and a settle frame so a stopped object's velocity returns to zero.
  • Render extract - the only code that writes entity state into the RenderScene; incremental, driven by RenderDirty and EnTT signals; instance slots are handed out in CreationOrder.
  • RenderScene - mesh arenas with one BLAS per mesh, material and instance tables, a light table in raster and RT layouts, per-frame-slot staging, a retire queue for replaced buffers, and a TLAS that is built on structural change and refit otherwise.
Why a persistent GPU scene

Nothing is rebuilt per frame. A still scene records no copies and no acceleration-structure work; a moving instance costs one slot upload and a TLAS refit. Deferred raster and every RT pass read the same tables.

Asset load workflow

From file to entities
  1. ModelLoader::load picks a parser by extension: OBJ to the native parser, FBX to ufbx then Assimp, everything else (GLB / GLTF) to Assimp
  2. env_demo and turntable call Model::loadFromGLTF (tinygltf) directly
  3. Every facade result goes through repairMeshNormals, which re-averages normals by position
  4. The result is a CPU Model with per-triangle material ids for multi-material meshes
  5. The caller registers the mesh and materials with the RenderScene and spawns entities carrying MeshRenderer

Loaders do not touch Vulkan or the registry. Nothing walks the node tree: meshes are concatenated in file order. Details in the loaders unit.

Hand-off to renderer

Contract at the boundary:

  • The renderer never includes EnTT; it sees only a RenderScene
  • MeshRenderer becomes one instance slot: world and previous-world matrices, mesh index, up to 64 material references, a visibility flag
  • Light and EmissiveProxyLight become one sorted light list, resolved to world space and packed for raster (8 lights) and RT (64)
  • The slot number is the raster firstInstance and the TLAS instanceCustomIndex
  • registerMesh is blocking load-time work; per-frame edits are staged copies recorded by recordUpdates
Design

The ECS never includes vulkan.h

World, transform and extract tests run without a GPU. The RenderScene is the single Vulkan-side owner of scene data.
