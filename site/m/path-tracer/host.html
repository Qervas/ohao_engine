Five steps that do not commute

`PathTracer` is the largest single owner of GPU state in the engine: roughly thirty images, a descriptor set per frame in flight, an RT pipeline, a shader binding table, and five optional denoise/post backends held by pointer. `init()` runs five build steps whose order is forced by data dependencies, not taste: `createRTPipeline` needs the descriptor set layout to build a pipeline layout, and `createShaderBindingTable` needs the finished pipeline to query group handles plus `vkGetBufferDeviceAddress` to publish the SBT's strided regions — which is itself resolved in step one.

Step one exists for three of the four pointers it fetches. `vkCreateRayTracingPipelinesKHR`, `vkGetRayTracingShaderGroupHandlesKHR` and `vkCmdTraceRaysKHR` are `KHR` extension entry points that no loader exports as core symbols; they are looked up by name on the device and the whole init aborts if any comes back null — the cheapest place to discover that a device advertised the extension but the driver did not deliver it.

return vkCreateRayTracingPipelinesKHR && vkGetRayTracingShaderGroupHandlesKHR &&ohao/render/rt/path_tracer.cpp:48

The fourth pointer the same function loads is not a ray-tracing entry point and does not share that justification. It is fetched under the unsuffixed name `vkGetBufferDeviceAddress` — core Vulkan since 1.2 — and the instance is created with `apiVersion = VK_API_VERSION_1_3`, so on a conforming loader it cannot come back null and its term in the `&&` chain is dead.

(PFN_vkGetBufferDeviceAddress)vkGetDeviceProcAddr(m_device, "vkGetBufferDeviceAddress");ohao/render/rt/path_tracer.cpp:46
.apiVersion = VK_API_VERSION_1_3, // Vulkan 1.3 for RT + buffer device addressohao/gpu/vulkan/device_setup.cpp:19

One number in the pipeline create-info is worth pausing on. It declares a maximum ray recursion depth of two, with a comment that path tracing "needs bounce recursion" — but the bounce loop in every raygen variant is iterative, and no closest-hit, any-hit or miss shader in `shaders/rt/` calls `traceRayEXT`. Every ray is launched from the raygen, so the pipeline never recurses past depth one.

pipelineInfo.maxPipelineRayRecursionDepth = 2; // path tracing needs bounce recursionohao/render/rt/path_tracer_pipeline.cpp:176

Render resolution is not output resolution

The caller passes display dimensions; `PathTracer` keeps two pairs. `m_outW/m_outH` is what was asked for, `m_width/m_height` is what the raygen dispatch and every AOV are sized to. They are equal in every mode except a DLSS upscaling preset, where `computeRenderResolution()` shrinks the render pair.

computeRenderResolution(); // sets m_width/m_height (render res)ohao/render/rt/path_tracer.cpp:89

The shrink is not a plain multiply: DLSS wants even dimensions, so the scaled value is masked down to even and floored at two — the render resolution is therefore almost never exactly `scale × output`.

v &= ~1u; // align down to evenohao/render/rt/path_tracer.cpp:302

Two images escape the render pair, and both are sized to *output*. The RGBA8 beauty is the first: under upscaling it is the full-res target the DLSS tonemap writes, so the raygen's own beauty store into it at render size is discarded.

imageInfo.extent = {m_outW, m_outH, 1};ohao/render/rt/path_tracer_images.cpp:65

The second is the DLSS-RR `COLOR_OUT` image — RGBA16F, allocated at the end of the same `createImages()` behind `#ifdef OHAO_DLSS_ENABLED`. It is what DLSS upscales the render-res guide buffers *into*, which is exactly why it cannot be render-sized; the DLSS tonemap compute then reads it and writes the RGBA8 beauty. Both exceptions therefore exist for the same reason, and both are live in the one mode where render and output differ.

if (vkCreateImage(m_device, &imageInfo, nullptr, &m_dlssColorOutImage) != VK_SUCCESS) return false;ohao/render/rt/path_tracer_images.cpp:980

`init()` runs before any denoise mode has been applied, so the scale there is always 1. A later `setRenderSettings()` that switches into DLSS-RR is what triggers the device-idle, destroy-all-images, recreate-all-images pass.

Why dead members are compiled into every build

Why

The NRD members — `unique_ptr<NrdDenoiser>`, `NrdCompositor`, `NrdCinematicPost` — are declared unconditionally in the header even when NRD is off; only the method bodies that touch them are `#ifdef`-guarded. The rejected alternative, wrapping the members in `#ifdef OHAO_NRD_ENABLED` like the DLSS block below them, is an ODR violation here: that macro is `PRIVATE` to one library, while a second library also instantiates `PathTracer`'s layout through `rt_profile_renderer.hpp`. {{cite ohao/render/CMakeLists.txt "target_compile_definitions(ohao_renderer PRIVATE OHAO_NRD_ENABLED)"}} The DLSS members *can* be conditional precisely because that macro is defined on both targets, keeping the layout identical. The asymmetry in the header is a faithful mirror of the build graph; flipping either side silently changes `sizeof(PathTracer)` in half the program. {{cite ohao/gpu/vulkan/CMakeLists.txt "target_compile_definitions(ohao_gpu_vulkan PRIVATE OHAO_DLSS_ENABLED)"}}

The same incompleteness forces the constructor and destructor out of line: a `unique_ptr` to a forward-declared denoiser cannot instantiate its deleter in the header. Both live in `path_tracer.cpp`, the one translation unit that includes every backend's real header.

One descriptor set per frame slot, rewritten every frame

There is no descriptor caching: the pool holds one set per frame in flight, and `render()` rebuilds up to thirty-seven writes from scratch into the set of the frame slot it is given before every trace. The array is sized with three entries of slack above the worst case, so adding more than three unconditional bindings without growing it overruns a stack buffer.

VkWriteDescriptorSet writes[40] = {};ohao/render/rt/path_tracer_render.cpp:144

The scene bindings are not owned here. `setSceneBuffers` copies the handles the `RenderScene` currently exposes — TLAS, arenas, tables, instance buffers and the light buffer — and it is called every frame after `recordUpdates`, because table growth and TLAS storage replacement hand out new handles. `render()` refuses to trace until every one of them is non-null, so there is no dummy buffer to fall back to.

!m_instances || !m_materialRefs || !m_lightBuffer) return;ohao/render/rt/path_tracer_render.cpp:44

Rewriting a set is only defined if no pending submission still references it, and the per-slot layout is what establishes that. `renderRTPipeline()` waits on the fence of the frame slot it is about to reuse — frame *N−3* — and `MAX_FRAMES_IN_FLIGHT` is 3, so frames *N−1* and *N−2* can still be executing, but they read their own sets. The write lands on a set whose last user has completed.

* 1. At frame start: waitForFrame(currentFrame) - blocks until frame N-3 completesohao/render/frame/frame_resources.hpp:65

Of the 37 bindings only binding 12 carries `UPDATE_AFTER_BIND`; the others rely on that per-slot ordering. The one place the ordering does not reach is a buffer the set *points at*: a handle that `RenderScene` replaces mid-flight stays alive in its retire queue for `MAX_FRAMES_IN_FLIGHT` frames, so a set still bound by an earlier frame never dangles.

256 bytes, and the word that had to hold two numbers

The push-constant block is asserted at 256 bytes — the device maximum on most RT GPUs — so when a genuine per-frame sample count was needed there was no room to append a field. It went into the high half of the word that already held the bounce limit.

const uint32_t packedBouncesAndSpf = (spf << 16) | (m_maxBounces & 0xFFFFu);ohao/render/rt/path_tracer_render.cpp:664

Only the realtime raygen unpacks the high half and loops on it; the base and offline raygens mask it off and trace one path per dispatch. The same push constant means two different things depending on which SPIR-V the profile loaded.

uint samplesPerFrame = max(pc.params.w >> 16, 1u);shaders/rt/pt_raygen_realtime.rgen:286

The jitter is computed on the host

No mode samples at pixel centre. Every raygen already draws its own stochastic sub-pixel offset per sample — `getSample2D(dimIdx) - 0.5` — and adds it to the primary-ray UV in all denoise modes.

vec2 uv = (vec2(pixel) + 0.5 + jitter + pc.jitter.xy) / vec2(pc.params.xy);shaders/rt/pt_raygen_realtime.rgen:303

What the host contributes, and only when the mode is NRD or DLSS-RR, is the second term in that sum: `pc.jitter.xy`, a *deterministic* offset. Determinism is the whole point — the same numbers are handed to the denoiser so it can subtract them during temporal reprojection. NRD receives them as `cameraJitter`/`cameraJitterPrev`; DLSS-RR receives them negated as `InJitterOffsetX/Y`. A shift the denoiser could not name would misalign history rather than widen the footprint. The offset is the radical inverse of the frame index in bases 2 and 3 — the Halton sequence — recentred on zero:

$$ \Phi_b(i) = \sum_{k \ge 0} d_k\, b^{-(k+1)}, \qquad i = \sum_{k \ge 0} d_k\, b^{k}, \qquad \mathbf{j}_n = \big(\Phi_2(i_n) - \tfrac12,\; \Phi_3(i_n) - \tfrac12\big) $$

$b$ is the base, $d_k$ the digits of index $i$ in that base, and $\mathbf{j}_n$ the pixel offset for frame $n$. The loop in `render()` is that sum written out, with `f` accumulating $b^{-(k+1)}$. The index is taken modulo 16 and then incremented, because $\Phi_b(0) = 0$ would spend one of the sixteen slots on "no jitter at all". Every other denoise mode gets `pc.jitter.xy = 0` and keeps only the sampler's own random offset.

const uint32_t idx = (m_haltonIndex % 16u) + 1u;ohao/render/rt/path_tracer_render.cpp:89
camera.jitter = {m_jitterCurrent.x, m_jitterCurrent.y};ohao/render/rt/path_tracer_render.cpp:862
evalParams.InJitterOffsetX = -in.jitterX;ohao/render/rt/denoise/dlss_rr.cpp:293

Two counters, and the clear that never happens

`m_sampleIndex` and `m_historyFrameCount` both advance once per frame and are not interchangeable: the first seeds the sampler, the second drives temporal logic. A reset sends the history counter to zero but restores the sample index to a caller-settable seed rather than zero, so a caller can replay an identical sample sequence across runs that change something else.

m_sampleIndex = m_renderSeed;ohao/render/rt/path_tracer.cpp:199

Setting the seed while the index still sits at the old one — nothing traced since the last reset — moves the index too, so a seed set after construction applies to the very next frame rather than only after the next reset:

if (m_sampleIndex == m_renderSeed) m_sampleIndex = seed;ohao/render/rt/path_tracer.hpp:183

The accumulation buffer is never cleared. On the frame where the history counter is zero its barrier declares the old layout `UNDEFINED`, licensing the driver to discard the contents; on every later frame the same barrier is a `GENERAL → GENERAL` read-modify-write acquire.

accumBarrier.oldLayout = (m_historyFrameCount == 0) ? VK_IMAGE_LAYOUT_UNDEFINED : VK_IMAGE_LAYOUT_GENERAL;ohao/render/rt/path_tracer_render.cpp:415

The post-processing images use the same idiom with per-instance latch booleans instead of a shared counter — and `createImages()` re-arms them, so a resize re-fires the `UNDEFINED → GENERAL` transition on the freshly created `VkImage` instead of trusting a stale "already transitioned".

m_nrdComposeFirstFrame = true;ohao/render/rt/path_tracer_images.cpp:802

Seven images only one raygen reads

The descriptor set layout declares 37 bindings, numbered 0–37 with 3 unused. Bindings 29–34 are the ReSTIR GI reservoir ping-pong and 35 is the DLSS specular hit-distance guide; all seven images are created and destroyed with the rest, and only the realtime raygen declares them. It cannot store to all of them: 29–31 are the *prev* half of the ping-pong, declared `readonly` and only ever `imageLoad`ed. Stores go to 32–34, the *curr* half declared `writeonly`, and to 35.

for (uint32_t b = 29; b <= 34; ++b) add(b, IMAGE, RGEN);ohao/render/rt/path_tracer_descriptors.cpp:85
layout(set = 0, binding = 29, rgba32f) uniform readonly image2D prevGIReservoir0;shaders/rt/pt_raygen_realtime.rgen:31

The per-frame rewrite fills all seven in every set, whichever profile owns the `PathTracer`, swapping prev and curr each frame. It has to: the realtime raygen touches them every frame, only binding 12 carries `PARTIALLY_BOUND`, and with these bindings left unwritten `rt_realtime` lost the device. A barrier takes all seven to `GENERAL` before the trace — the reservoirs from `UNDEFINED` until their half of the ping-pong has been written once, the hit-distance guide from `UNDEFINED` every frame, since the raygen rewrites it whole.

addImage(35, &specHitDistInfo);ohao/render/rt/path_tracer_render.cpp:403
Key idea

`PathTracer` holds only *borrowed* handles for scene data. The environment CDF buffers and the env map view and sampler belong to `VulkanRenderer`; the TLAS, arenas, tables and light buffer belong to `RenderScene`; `destroy()` nulls the cached CDF handles rather than freeing them, because freeing them here would double-free. {{cite ohao/render/rt/path_tracer.cpp "m_envMarginalCDFBuffer = VK_NULL_HANDLE;"}}

Contracts

  • `init()` must not be reordered: function pointers first, descriptor layout before pipeline layout, pipeline before SBT.
  • The two profile renderers each own a full `PathTracer`, and each `PathTracer` allocates its own set of roughly thirty images, so an eager pair doubles the render-target footprint. They are created lazily on the first `setRenderMode()` into that mode instead.
  • Each frame slot's descriptor set is rewritten from the host at the top of `render()`, and bindings 13–16 flip between ping-pong views each frame, so the rewrite is not idempotent. It is safe because the slot's fence was waited first; calling `render()` with a slot whose fence was not waited rewrites a set an earlier submission still reads.
  • `setSceneBuffers` must run every frame after `RenderScene::recordUpdates`. A handle cached from an earlier frame may belong to a buffer or TLAS that has since been replaced and retired.
  • `destroy()` waits for device idle, tears down the denoisers, nulls the borrowed CDF handles, and only then destroys the SBT, pipeline, descriptors and images. The destructor calls it, so an object outliving its `VkDevice` is a use-after-free.
  • Switching to or from a DLSS upscaling preset reallocates every render target, so `setRenderSettings()` is safe only between frames — never inside a command buffer.
  • The `PathTracerShaderSet` defaults name `rt_pt_raygen.rgen.spv`, but both shipped profiles pass explicit sets (`..._realtime`, `..._offline`), so the default never loads in-tree.
