One sequence, in an order that matters

OHAO has no editor host. The offline examples — `cornell_box`, `model_viewer`, `env_demo`, `turntable` — are thin `main()`s over one sequence: construct a `VulkanRenderer` at a fixed output size, bring up the device, create an `ecs::World` and wire its render extract (and, for a world built from data, instantiate) to the renderer's `RenderScene`, build entities, apply the world's camera and environment, choose a `RenderMode`, then loop `world.update()` and `render()` and read the pixels back. `ohao run --render` runs the same sequence on a scene file. `cornell_box` is the shortest complete instance of it, and it shows the one convention that surprises people reading the CLI: the output resolution is a compile-time constant in the driver, never an argument — 1920×1080 in `cornell_box`, `model_viewer` and `env_demo`, 1280×720 in `turntable`.

const uint32_t W = 1920, H = 1080;examples/cornell_box.cpp:51

The windowed host, `ohao_game`, runs the same sequence through `ohao_runtime`'s `Application` with two substitutions: the renderer is sized from the window's framebuffer extent and initialised against a present target, and the loop presents to a swapchain instead of reading pixels back. `Application` also owns the `ecs::World` and installs the extract itself:

if (!m_renderer->initialize(m_window.presentTarget(cfg.vsync))) {ohao/runtime/application.cpp:14

Scene construction takes one of two forms. `cornell_box` and `model_viewer` build the entities a scene file holds — a `MeshSource` naming a primitive or a model path, a `MaterialOverride`, lights, a `Camera` and an `Environment` — and install instantiate, which builds each GPU mesh on the first update:

ecs::installInstantiate(world, renderer.renderScene(), renderer.getTextureManager(), assets);examples/cornell_box.cpp:68

`env_demo`, `turntable` and `ohao_game` still call the `spawn` helpers, which upload directly. `spawnModel` registers the mesh and its materials with the `RenderScene` — an upload and a BLAS build, blocking, at load time — and returns an entity carrying a `MeshRenderer` that holds the handles:

entt::entity spawnModel(World& world, render::RenderScene& scene, BindlessTextureManager* textures,ohao/ecs/spawn.hpp:39

`spawnLight` makes an entity with a `Light`. Neither path touches a command buffer, and neither makes anything visible yet: an entity reaches the screen only after a `world.update()`.

The frame, from game hooks to passes

One frame is the same chain in every host. In `ohao_game` the loop runs the fixed-step game hook zero or more times, the per-frame hook once, then the world, then the renderer:

m_world->update(frameDt);ohao/runtime/application.cpp:49

The headless drivers have no `Application`, so they call `world.update(0.0f)` before each `render()` themselves. The world runs its systems in exactly the order they were added. The constructor adds two: the engine-provided `spin`, which turns entities carrying a `Spin` (a no-op at `dt = 0`, which is why headless renders are unaffected), then the structural `transform`:

addSystem("transform", [](World& w, float) { updateTransforms(w.registry()); });ohao/ecs/world.cpp:56

Instantiate, when installed, goes immediately before `transform`, so a mesh it builds gets its world matrix in the same update. `TransformSystem` recomputes `WorldTransform` for every dirty entity and its descendants, parents first, and tags the movers `RenderDirty`. The render extract is installed straight after it and consumes those tags:

world.addSystemAfter("transform", "render_extract",ohao/ecs/render_extract.cpp:231

It releases the slots of vanished renderables, creates an instance for every renderable without one — in creation order, so slot numbers are deterministic — rewrites the moved ones, and rebuilds the light list when a light changed. All of that is host-side: `createInstance`, `updateInstance` and `setLights` edit the `RenderScene`'s tables and mark entries dirty. Nothing reaches device memory until the renderer records its frame. There the first thing in the command buffer, ahead of every pass, is the `RenderScene`'s own update:

void recordUpdates(VkCommandBuffer cmd, uint32_t frameSlot);ohao/render/scene/render_scene.hpp:57

`recordUpdates` copies the dirty instance, material and light rows from the frame slot's staging buffer into the device-local tables, then builds or refits the TLAS. The slot's fence has already been waited on, so a host edit can never race a frame still in flight. The deferred chain follows it in the same command buffer; on the RT path the profile is handed the freshly updated buffers first:

rtRenderer->setSceneBuffers(*m_renderScene);ohao/gpu/vulkan/render_dispatch.cpp:251

So the order is game hooks → spin → instantiate → `TransformSystem` → `RenderExtract` → `RenderScene::recordUpdates` → passes, and every arrow is a one-way hand-off.

Two mistakes in that order fail silently. `renderScene()` dereferences the renderer's `RenderScene` without a check, and that object exists only after `initialize()` has run:

[[nodiscard]] render::RenderScene& renderScene() { return *m_renderScene; }ohao/gpu/vulkan/renderer.hpp:193

Call it first and you hold a null reference. And an entity spawned into a world whose extract was never installed keeps its mesh and materials in the scene but never gets an instance, so no pass has anything to draw. The rest of the chain runs anyway, and the Preetham sky pass is on by default, so what lands is an empty sky-lit frame — not black, and not an error either.

bool m_skyEnabled{true};ohao/render/deferred/deferred_renderer.hpp:194

Teardown runs the same chain backwards. The world holds `RenderScene` slots, so it goes first, while the scene still exists:

m_world.reset(); // releases its RenderScene slots while the RenderScene existsohao/runtime/application.cpp:74

Why ray tracing has nothing to replay

`setRenderMode()` is where ray tracing actually comes into existence. The renderer deliberately does *not* create a path tracer during `initialize()`:

// created lazily on setRenderMode() (eager dual init at 4K can OOM).ohao/gpu/vulkan/renderer.cpp:165

What it does create is the `RenderScene`, which owns the BLAS per mesh and the TLAS over the instance table whether or not any path tracer exists. So a profile created later has nothing to catch up on: the scene data lives in the render world, not in the profile. `ensureRTRenderer` constructs the profile and returns, with a comment saying why nothing else is needed:

// Scene buffers, textures and lights are bound every RT frame from theohao/gpu/vulkan/renderer.cpp:331

Each RT frame the renderer binds the tables, the bindless texture list and the environment resources into the profile's descriptor set before dispatch. A driver may therefore select its mode before or after spawning — both orders cost the same, one upload, and neither needs a replay.

Why

The rejected alternative is eager construction: build both the realtime and the offline `PathTracer` in `initialize()`. It lost on memory. Each profile owns a beauty image plus the full AOV set at output resolution — motion vectors, depth, roughness, split diffuse/specular radiance, albedo, normal-roughness — and the source states the hazard as a possibility, not a measurement: eager dual init *can* OOM at 4K. No shipped driver renders at 4K, so at the resolutions the examples actually hardcode the avoided cost is a projection, not observed history. Lazy construction is cheap to keep because scene data no longer lives in the profile: creating one later copies nothing.

Mode selection can also fail closed. If RT is unavailable, `setRenderMode` prints and returns *without* assigning `m_renderMode`, leaving the renderer in whatever mode it already had — which at startup is `Deferred`.

std::cerr << "Path tracing not available, staying in current mode" << std::endl;ohao/gpu/vulkan/renderer.cpp:340
RenderMode m_renderMode{RenderMode::Deferred};ohao/gpu/vulkan/renderer.hpp:433

So an RT request on a device without ray tracing renders deferred instead, and the examples print the mode they *requested*, not the one the renderer accepted, so a silent downgrade reads as success on stdout.

Three deep, and the +3 in every driver

The offline drivers all render more frames than the user asked for, by exactly three:

const int frames = cli.useDeferred ? 10 : (samples + 3);examples/cornell_box.cpp:84

That constant is not a fudge factor. Frame resources are a ring of three, and the RT dispatch path reads pixels out of the same slot it is about to overwrite — after waiting on that slot's fence, which is the fence signalled three calls ago.

constexpr uint32_t MAX_FRAMES_IN_FLIGHT = 3;ohao/render/frame/frame_resources.hpp:19
// Read back previous frame's pixelsohao/gpu/vulkan/render_dispatch.cpp:220

So the CPU-visible pixel buffer always lags the GPU by the ring depth. With `samplesPerFrame` at its default of 1, one `render()` call adds one sample to the accumulator, and the last copy of a loop of `samples + 3` calls happens at `k = samples + 2`, delivering the image produced at `k = samples - 1` — the frame after which exactly `samples` samples have been integrated. The overshoot drains the pipeline and lands on the requested budget with nothing wasted.

Deferred takes the other branch of that ternary and renders a fixed count that ignores the sample argument entirely — in raster mode the spp number on the command line does nothing. The headless deferred path reads back through the same ring, so its fixed count only has to exceed the ring depth. The constant is per-driver, not engine-wide: ten in `cornell_box`, thirty in `model_viewer`.

const int frames = cli.useDeferred ? 30 : (samples + 3);examples/model_viewer.cpp:207

Three different exits from the GPU

`getPixels()` has three exits behind one signature, and which one runs depends on the denoiser. `None`, `Atrous` and `DLSSRR` share the first: return the ring buffer described above. `None` does nothing to it; `Atrous` denoises the beauty image (`m_outputImage`) in place on the GPU, and the DLSSRR path, when it runs at all, tonemaps into that same image — so neither needs a readback of its own.

if (m_denoiseMode == DenoiseMode::None || m_denoiseMode == DenoiseMode::Atrous ||ohao/gpu/vulkan/renderer.cpp:648

NRD takes the second, and it touches neither the ring nor the accumulator: it copies the tracer's RGBA8 tonemapped image — already denoised and tonemapped on the GPU — straight into host memory behind a `vkQueueWaitIdle` on the graphics queue.

VkImage srcImage = getNrdTonemappedAOVImage();ohao/gpu/vulkan/renderer.cpp:1603

OIDN takes the third: a full `vkDeviceWaitIdle`, then three float readbacks — the accumulation image plus the albedo and normal AOVs — into host memory, where the CPU denoiser runs over them.

bool ok = readbackImage(rtRenderer->getAccumImage(), beauty);ohao/gpu/vulkan/render_dispatch.cpp:469

That third path matters because the offline profile denoises by default:

.denoiseMode = DenoiseMode::OIDN,ohao/render/rt/rt_settings.hpp:60

so a plain `cornell_box out.png 1024` writes a PNG denoised from an accumulator holding 1027 samples, not 1024 — the three drain frames are still real samples, and a readback that reads the accumulator directly sees them. The `+3` padding is what makes `--denoise=none` land on the exact budget; under the default it is three free samples on top of it. The result of either non-ring path is cached in a `mutable` buffer and invalidated at the end of every `render()`, so calling `getPixels()` twice per frame costs one denoise, not two. The call is declared `const` and is not: both non-ring branches `const_cast` away constness to allocate a command buffer, submit it, and block. The comment in the source is honest that this is only safe after `render()` returns on a single thread.

The settings reset that eats your overrides

Once the loop starts, the renderer re-derives its RT settings from the pipeline object on every single frame:

m_rtSettings = pipeline.getDefaultSettings();ohao/gpu/vulkan/renderer.cpp:407

An override a driver configured once does not survive even to its first dispatch. `renderRTPipeline` calls `prepareRTSceneForFrame` — the function that performs that reset — before it records the command buffer that dispatches the tracer:

prepareRTSceneForFrame(pipeline);ohao/gpu/vulkan/render_dispatch.cpp:231

The same call is where the frame's scene-side bindings are refreshed — the light buffer, the bindless texture list, the environment CDFs and the HDRI scale — so it is the single per-frame seam between the renderer and the `RenderScene`. Four values are explicitly re-injected around the reset — anisotropy strength and rotation, subsurface strength, and the realtime per-frame sample count:

// so restore the user's choice here (same pattern as aniso/SSS preservation).ohao/gpu/vulkan/renderer.cpp:383

The denoiser gets a different mechanism: `setDenoiseMode()` raises a sticky `m_denoiseModeOverridden` flag that blocks the per-frame resync, and the override is pushed down into the tracer's own settings for exactly two modes, `Atrous` and `DLSSRR`.

m_rtSettings.denoiseMode = m_denoiseMode;ohao/gpu/vulkan/renderer.cpp:379

`Atrous` needs it because the RT pipeline dispatches that denoiser itself, in place on the beauty image. `DLSSRR` rides the same branch, but the tree disagrees with itself about what it does: `path_tracer_render.cpp` holds a real NGX evaluate-and-tonemap block, compiled out unless the vendored NGX static library is present, while `getPixels` still carries a Phase-1 comment saying DLSSRR does not dispatch denoising at all.

// Phase 1: DLSSRR does not yet dispatch denoising (foundation only) — theohao/gpu/vulkan/renderer.cpp:646

OIDN is the one genuinely consumer-side mode — it runs on the CPU after readback. NRD is dispatched inside the RT pipeline like `Atrous`, but off a different gate: the tracer runs it whenever the denoiser initialized and the profile enables auxiliary AOVs, and never reads `denoiseMode` to decide, so pushing the override down would buy it nothing.

if (m_nrdDenoiser && m_renderSettings.enableAuxiliaryAOVs) {ohao/render/rt/path_tracer_render.cpp:840
Key idea

Scene data reaches the GPU along one chain — game hooks, spin, instantiate, `TransformSystem`, `RenderExtract`, `RenderScene::recordUpdates`, passes — and there is one authority over RT behaviour (the active `IRTRenderPipeline`, reasserted every frame). Ordering mistakes around the chain fail *silently* — an extract that was never installed, a refused mode, a stale override — never with an error. When an OHAO driver renders an empty frame or ignores a flag, suspect call order before suspecting the shaders.

Contracts

  • `initialize()` must precede `renderScene()`. Before it, the `RenderScene` does not exist and the accessor returns a null reference.
  • Install the render extract (`ecs::installRenderExtract`, or let `Application` do it) before expecting entities on screen, and run `world.update()` before every `render()`. Spawning uploads a mesh and its materials; only the extract makes an instance of it.
  • The `RenderScene` must outlive the `ecs::World`. `Application` resets the world first; in `cornell_box` the `VulkanRenderer` is declared above the `ecs::World`, so reverse declaration order destroys the world first.
  • `setRenderMode()` may refuse. Read back `getRenderMode()` rather than trusting the value you passed; the examples do not, and print the requested mode.
  • In the modes that return the ring buffer (None, Atrous, DLSSRR) the pixels trail the GPU by `MAX_FRAMES_IN_FLIGHT` calls. Reading them after fewer than four `render()` calls returns a staging slot that was never written.
  • Any new per-run RT setting must be re-injected in `applyRTRenderSettings`, or the `getDefaultSettings()` reset inside `prepareRTSceneForFrame` silently reverts it before the next dispatch.
