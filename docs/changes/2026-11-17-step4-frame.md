# Step 4: the frame

**Spec:** `docs/specs/2026-11-08-system-design.md`, 4.5, 4.6 and 5 (step 4); plan `docs/plans/2026-11-11-step4-frame.md`.
**Status:** built 2026-11-11 to 2026-11-17: 4a (every pass declares what it touches). 4b (jobs, parallel waves, Jolt
on jobs, the frame packet, the render thread) measured and not built.

## 1. Summary

Every pass of both renderers records through one pass type, `render::Pass`: it says what it reads and writes, and
the barriers, image layouts and the rendering's attachments follow from that and from the state each image and
buffer carries across passes and frames. Every image and buffer comes from one allocator, named, and is given back
after the frames in flight. The build refuses a hand-written barrier, render pass, framebuffer or raw allocation
anywhere else. Moving the passes found five bugs in the old code; synchronization validation, which reported a
hazard before, is silent. The GPU frame is no slower; recording costs the CPU 0.01 to 0.09 ms more.

## 2. What was built

- **`render::Pass`** (`ohao/render/graph/pass.{hpp,cpp}`): usages for images (sampled, storage read, write and
  read-write, colour and depth attachments with their load, depth read, copy, present) per mip and layer, and for
  buffers (uniform, storage, indirect, vertex, index, copy, host read, acceleration-structure input and storage).
  Barriers are `synchronization2`, batched into one call per pass. `render::Timed` puts several passes under one
  timer. External code with barriers of its own (NRD, DLSS) is one pass that declares what it needs and `leaves`
  what it leaves.
- **`gpu::Image`** (`ohao/gpu/vulkan/gpu_image.hpp`) on `GpuAllocator`: a named image with its views and a state per
  mip and layer; `retire` destroys an image or buffer `kRetireFrames` frames later. `GpuBuffer` carries its state.
  One allocator serves the renderer, the scene and the texture table.
- **`render::createGraphicsPipeline`** (`render/graph/pipeline.hpp`): every raster pipeline, for dynamic rendering.
- **The rule** (`tools/check.py`, `FRAME_RULE`): `vkCmdPipelineBarrier`, `vkCreateRenderPass`, `vkCreateFramebuffer`,
  `vkCmdBeginRenderPass`, `vkAllocateMemory` and `vkCreateImage` fail the build outside `render/graph` and
  `gpu/vulkan`.
- **`render.stats`** `memory.targets`: the renderer's images by name, largest first; `targetBytes`, `deviceBytes`.
- **Deleted:** the old `render_graph`, `rtc::Image` and its transitions, `rtc::HostBuffer`, `render_pass_base.cpp`,
  12 `VkRenderPass` objects and their framebuffers, first-use flags, file-local barrier helpers, ten per-AOV
  readbacks and 19 renderer image getters nobody called, `setTonemappingEnabled` (no caller).

## 3. Bugs found and fixed

1. **A write-after-write on the G-buffer depth** in the play scene and the smoke doorway (`OHAO_VALIDATION=sync`, on
   the commit before the step too; the validation gate runs without synchronization validation). The old graph forgot
   its images each frame, so its first barrier on the depth did not wait for the transparent pass's render pass,
   which stores it. Shown by A/B: forgetting the G-buffer's states each frame reproduces it.
2. **A released mesh's BLAS buffer** was destroyed while later frames' barriers named it
   (`VUID-vkDestroyBuffer-00922`): it is retired with the frames in flight.
3. **The gizmo** destroyed its buffers under frames in flight, and its render pass named an sRGB format for a UNORM
   target.
4. **The OIDN readback** took its guide images in the wrong layout (`VUID-09600`).
5. **The DLSS tonemap call** passed its arguments in the wrong order. Fixed, not run: no DLSS SDK on this machine.
6. **A GPU fault this step caused** (2026-11-11 20:04, `Xid 31`, an MMU fault, during `rt.gi`; the engine reported
   the hang at the 2 s fence and exited 5). A by-hand check replaced the sky map three times after the device wait
   before a replace was removed. The texture table freed the old map's slot and handed the same slot to the new map
   at once (the log: `bindless idx=8` at every replace), rewriting a descriptor frames on the GPU still read;
   validation cannot see it (`UPDATE_UNUSED_WHILE_PENDING` makes it the application's promise). Not reproduced on
   purpose. Fixed: a view registered from outside is retired after the frames in flight; the wait before a sky replace
   and the one before a render-scale change are back. After a full power-off, the sequence ran clean three times.

## 4. Spec corrections

Made in `docs/specs/2026-11-08-system-design.md`:
- **4.5:** the frame packet, render thread, job system and Jolt on jobs are not built; the measurements are there.
- **4.6:** no graph object (passes run in the order the code writes them: no reordering, culling or async compute);
  no pipeline library, shader hot reload, single bindless table, generated parameter blocks or transfer queue.
- **Step 4's done-when:** `replay_test` at 1 and N threads and the CPU frame dropping with cores are dropped (the CPU
  frame is under half a millisecond).

## 6. Known gaps

- **CPU recording is 0.01 to 0.09 ms slower** than before the step, cause not found. The plan's "no slower on any
  scene" holds for the GPU frame only.
- **ReSTIR DI's images** are allocated at full resolution in its half-resolution mode (about 300 MB at 1080p could
  go); the idle renderer's images are kept when the mode switches; no image aliasing. Each is a renderer change with
  its own measurement.
- **Not run:** the DLSS branch (no SDK); the swapchain blit beyond the bounded window runs.
- **33 device waits** remain (section 2); the ones outside shutdown and resize are each for a rare event.
- **The texture table's uploads** keep their own barriers inside `gpu/vulkan`, which cannot include `render/`.
- `site/tools/monograph/tree/deferred.py` still lists `render_pass_base.cpp` (the monograph is frozen).
